# Taskflow 研发工作台

左侧选择项目并进入设置，主区标题选择运行，流程与运行操作下方切换规划、开发任务、需求和代码验收。开发任务可切换依赖图和计划清单。设置显示已生效的角色来源和后端自动交付就绪状态。

「Factory 全流程」接入固定版本 Agentic Software Factory 的原生图、配置和执行。首次运行 `npm run factory:install`，在 Taskflow 项目内打开入口，选择专用 Git 工作区或授权仓库。可交接当前已确认的设计规格。[使用方式和功能对照](docs/FACTORY_WORKBENCH.md)。

在「开发任务」可拖动节点、平移或缩放画布，用小地图定位，点开任务核对输入、产出、验收和来源。打开「编辑连线」后，从一个任务的检查点拖线到后继任务，或用选择器添加。保存后重新确认计划。符合逐任务条件的工程计划可「保存为按图运行」，再确认当前版的逐任务联合验收清单。开发时每个检查点通过并集成后释放自己的后继，汇合等待所有直接输入。

新增**多 Agent 规格评审 v0.2 首版**：手动规格确认停点可启用六节点评审，专业提案、关联异议、人工裁决、新版本重审与规格/阶段清单联合确认已接入页面及持久化。当前使用明确标注的离线角色夹具，不调用真实模型；通过只放行规划，不代表软件验收。运行 `npm run spec-review:demo` 创建独立演示数据，`npm run spec-review:test` 执行相关免费回归。[流程与演示](docs/SPECIFICATION_MEETING.md)。

网页导航提供「API 服务」和「Agent 角色」两个入口。先在 API 服务页添加兼容 Chat Completions 的地址、模型和密钥，再在 Agent 角色页为规格、工程规划、测试提案、编码和代码审查分别选择服务。多个角色可以共用同一个服务，选择环境默认的角色沿用 `.env` 的 `LLM_*` 配置。保存后，新请求使用当前配置，正在运行的开发沿用启动时选定的编码和审查配置。

配置与加密密钥保存在本机 `DATA_DIR/agent-settings/`，页面仅显示密钥是否已设置。编辑时密钥留空保留原值，删除服务前先解除角色绑定。此处“应用”指本机 API 与角色配置，不会发布公网服务；目前只支持 Chat Completions 协议，角色职责与审批、测试及交付规则仍由平台控制。

模型规格整理和工程规划默认不限调用次数。网页「查看问题」支持逐题回答和模型自动追问。工程每轮自动修正最多10分钟，手动重试可开始新一轮。调用历史和待核对请求在重启后保留。

把软件需求文档转换为可审阅的设计规格、架构建议和 `task.md`，通过前端展示每个规划阶段的依赖、状态、日志与文档产物。

这是一个可以本地运行的课程项目。浏览器入口生成研发规划与文档；规格、计划及联合验收定义确认后，新路径可按当前计划生成真实多文件候选，运行独立HTTP、桌面/手机Edge和模型Review，合格后交付源码。当前完成了便笺小业务基准，复杂业务与逐任务并行仍在继续验收。原固定图书借阅参考保留独立入口。需求中的命令不会直接获得执行权限，文档成功不代表目标软件已完成。

新增**开发任务模拟编排**：已确认计划中的实际任务可创建独立模拟运行，按依赖、写入冲突、并发上限和人工确认推进，现有任务图展示后端状态。它与规划运行、固定参考源码执行分别记录，“模拟完成”不是编码、测试或软件验收。见[完整演示和限制](docs/SIMULATION.md)、[模拟接口](docs/API.md#开发任务模拟编排)。`npm run simulation:demo`生成单独演示数据，`npm run simulation:test`运行免费本地相关回归，不调用模型。

后续目标已明确为采用 Agent 主导开发方式，建设面向复杂全栈 Web 业务、支持持续需求变更的软件研发 Agent 平台。当前协作设计以 [新版 Word 文档](软件项目%20Agent%20协作流程%20开发编排新版.docx) 为依据，[DESIGN](docs/DESIGN.md) 提供同步 Markdown。高完成度目标见 [产品需求](docs/PRODUCT_REQUIREMENTS.md)，持续迭代方式见 [实现流程](docs/ROADMAP.md)。目标设计不代表现有代码已完成，当前运行能力仍以下文和验证记录为准。

## 启动

在项目目录执行`npm start`启动普通工作台，执行`npm start -- --demo`启动独立模拟示例（4320端口）。启动入口会先验证Node.js版本及`node:sqlite`，默认Node过旧时查找本机可用运行环境；不修改系统PATH。可设置`TASKFLOW_NODE`为合适node程序的绝对路径；显式配置无效时明确报错，不静默忽略。直接执行`node server.mjs`仍要求当前终端Node.js本身符合要求。

安装 Node.js 22.21 或以上版本，在项目目录执行：

```powershell
node --version
npm ci --ignore-scripts
npm start
```

浏览器打开 [本地工作台](http://127.0.0.1:4317)。停止服务时，在启动终端按 `Ctrl+C`。

平台锁定`playwright-core`作为独立浏览器验收依赖，使用系统Microsoft Edge；仅生成规划文档不启动验收浏览器。选择模型执行后，后端独立启动检查浏览器。`npm start` 在选定 Node 运行时下构建 React、TypeScript 和 Vite 前端，然后启动同源服务。改服务端时运行 `npm run dev`。同时改前端时，在另一终端运行 `npm run ui:watch` 并刷新页面。直接执行 `node server.mjs` 或单独运行浏览器测试前，先运行 `npm run ui:build`。

`npm test`将测试文件进程并发上限固定为4，控制同时运行的原生浏览器与MXC数量；测试项、业务断言和停止要求保持不变。本机默认24文件并发曾出现一次归档进程停止未确认，尚未确定具体原因；新测试会保存完整意外报告，并保留任何停止未确认的临时工作区，不能将其当作通过。

## 当前验收入口

当前统一按浏览器网页应用规划，采用平台提供的HTML/CSS/JavaScript、Node.js与SQLite；无需用户填写技术方案。Windows使用浏览器访问，不生成原生桌面安装包。已在本地启动时直接打开工作台；重新开机后在项目目录执行`npm start`。旧规格因选型未定而失败时，点击“采用默认方案并重新确认”，原文和回答保留，该步骤不调用模型；之后确认规格才会按页面预算请求工程设计。

可复现验收使用 `npm run acceptance`：固定示例、local模式、两次独立运行，校验规格/架构/任务/检查/导出ZIP的文档哈希和计划投影，不调用模型、不写用户数据；报告在 `output/acceptance-<时间>/`。提供与当前规则兼容的固定参考源码ZIP时，加 `--archive 路径` 可再执行固定HTTP/数据库和真实Edge检查。详见[可复现验收流程](docs/ACCEPTANCE.md)。

左侧项目名称旁“×”可删除项目，先核对确认弹窗中的名称。有实际在途任务、预览或进程状态待核对时不能删除；从工作区移除后仍保留本机恢复记录，不物理擦除日志和源码。验收删除时请先新建临时项目，不使用需要保留的项目。

默认方案、规划导出和模拟完成均不表示上传业务已实现。认可联合验收定义后，可在“按当前规划开发”生成真实候选；只有当前版本完整通过才能下载源码，原固定参考仍保留独立入口。

## 演示一条完整流程

新建项目并导入需求后，可点击「自动开发并交付」，一次确认模型用量。工作台会连续整理规格、检查和确认计划、生成并核对独立验收清单、编写代码、自检、运行 HTTP 与 Edge 测试并独立审查。首页展开九步进度，可从对应节点查看阶段证据；仅有业务问题时，需要在「查看问题」中提交答案，原运行随后继续。候选可修复的问题在本次开发预算内自动返工，最终通过才开放源码 ZIP。

请先配置五个 Agent 角色及本机隔离执行环境。自动运行每次最多 4 次规格、5 次工程和 3 次验收清单模型请求，随后启动一次开发执行。开发、测试、审查与返工共用 60 分钟的总时限。整体开发最多 6 次模型请求，逐任务开发最多 48 次。模型、环境、预算或验收故障会标明失败阶段并保留证据。需要逐步核对时，可选「手动规划」，沿用以下操作。

验收清单未通过时，自动重试会把缺失覆盖、错误依赖或响应格式反馈给测试 Agent。首次清单预算用尽且开发尚未启动时，可在同一运行点击「重试验收清单」，确认最多 3 次新增清单调用和后续开发。也可保存修订后的清单，用「使用已保存清单继续」进入开发，直接复用同一版本清单。原规格、计划与失败记录保留。页面关联需求须有可观察的浏览器断言，合格清单才进入执行。

工作台分为“规划与确认、开发任务、需求与功能、代码与验收”四个工作区，一次显示一处。规划流程默认展开，主页面整体滚动，导航吸顶，下方内容可以自然滚到屏幕中部；切换或刷新保留草稿与整页阅读位置。任务编辑就地打开侧边对话框，关闭后返回原任务图；功能填写、预览、保存和应用集中在需求工作区。规划、模拟及代码执行失败会在当前视口底部持续显示并预留操作空间，点击“查看问题”才定位，不自动打断输入。

首页在项目标题下显示九步流程图。没有项目时，点击「需求输入」可以新建项目；已有项目时，节点显示所选运行的实际进度，点击节点可进入对应的内容和操作。在「验收准备」核对用量并生成或导入清单；当前代码通过同版本测试与审查后，从「交付」进入预览和源码下载。任务图、版本和日志可直接从工作区导航打开。

在「代码与验收」选择一条开发执行，可分别查看编码与自检、独立测试和代码审查的进度与候选提交。整体开发可直接跳到对应记录。分任务开发时，点任务图节点查看该任务的角色和证据。

以下流程生成规划与文档；下方代码执行区域另按明确选定的固定参考契约执行。规划任务图仍是上传业务的待开发计划，不自动改成参考项目已经完成的任务。

1. 点击“新建项目”，再点击“载入示例”，或上传自己的 `.md`、`.txt`、`.docx` 软件需求文档。也可以直接粘贴需求文本。
2. 点击“创建项目”。选择本地规则模式，点击“开始编排”。
3. 模型模式下需要确认业务信息时，打开「查看问题」，逐题回答首版范围和验收所需的事项。提交后自动整理规格，只有这轮未明确的原题需要补答。草稿可单独保存。规格引用失败时可查看对应草案的标题、描述和模型尝试引用的文字，再用已保存的回答重新整理。问题答清后，核对规格和验收要求，点击「确认规格并继续」。驳回的版本必须实际修订后才能重新确认。
4. 规格确认后，架构与任务拆解并行执行。点击阶段查看日志、`architecture.md`、`task.md` 和检查报告；开发任务图仍表示待开发计划。
5. 运行停在“等待计划确认”时，核对任务粒度、依赖及验收。打开“开发任务”，点选节点后点击“修改此任务”，可直接定位编辑区，勾选前置任务和关联需求；修改预览显示前后内容，任务图标出未保存改动和需要核对的下游。保存新版本或退回修改，再点击“确认计划并导出”。每次确认只绑定当前版本；规格修订会使旧计划及确认失效。
6. 导出阶段完成后，下载单份 Markdown 或完整 ZIP 文档包。切换运行记录可以查看历史输入与产物。
7. 如需验证受控研发链路，在“代码执行与验收”中核对固定参考范围、配置模型及每次执行预算，勾选后启动。此操作真实调用模型并产生用量，需要本地有效MXC和Edge；没有保护环境时明确失败。页面显示实际提交、代码差异、每项预期/实际检查结果、Review、事件和未知/已知用量。
8. 可以请求停止；“已请求停止”与“已确认停止”分别展示。失败后按当前范围重新执行会创建新编码尝试；已有正常停止且来源完整的固定候选可“重新检查固定代码”，新增编码为0，全部检查和Review重跑。两者保留原失败及用量，须核对当前范围/预算并勾选。只有当前候选完整通过检查，才开放独立本地预览及已验收源码下载。预览也占用本次规划的活动槽，先停止预览才能再执行；状态待核对时不会自动启动下一轮。

已有候选被有效Review阻塞时，核对当前范围和修复预算，可选择“保留代码并修复”。新尝试读取原源码和完整阻塞意见，生成真实新代码版本，再逐项关闭原问题并重新运行完整检查；不会覆盖原失败报告与用量。只有无变化重审的“重新检查固定代码”不能清除这些阻塞；格式错误Review还不构成可用修复意见。

规划阶段的“成功”表示相应文档已生成并校验，不能代替两次人工确认或软件验收。修订和确认依据可在页面历史中查看。页面草稿及所选项目/运行在标签会话中保存，刷新不必重填。旧版运行继续按原导出流程展示，不伪造新版规格确认。`task.md`中的开发任务仍为待开发。

- [校园图书借阅系统](examples/library-system.md)：馆藏查询、借还、库存约束和管理权限。

## 暂停与失败恢复

暂停在阶段边界生效：已经启动的阶段会完成，后续阶段暂不启动。点击恢复后，编排器重新检查依赖并继续执行。

可在演示选项中给任务拆解、架构设计或检查阶段注入一次故障。例如让任务拆解首次失败：架构分支仍可完成，下游检查与导出被阻塞。运行结束后，选择失败阶段重试；成功分支不会重新执行，失败阶段的尝试次数和历史记录仍可查看。演示故障会明确记录在日志中。

需求输入需要改变时，展开“修改当前项目需求”，编辑正文或导入MD/TXT/DOCX，填写原因并保存为待应用变更。核对原文差异和影响后，再在规划与执行均空闲的检查点应用。保存和解析不调用模型；应用后旧运行只读，选择“再次编排”生成新规格与计划并重新确认。新运行会自动继承上一版运行已保存的回答（含澄清问题和问题答复），模型只面对新版正文和已有回答；重复问题会预填，增量问题才需要补充。新版正文优先，冲突时请修改预填答案。旧审批和检查仍保留历史归属，不继承到新版本；当前只更新需求输入，尚不自动修改已有目标代码或迁移业务数据库。执行、预览或进程状态待核对时不允许应用，待应用请求仍保留。

架构和任务共用工程请求。工程草案结构有误时，控制器给模型反馈具体原因。单次工程调用最多60秒，每轮自动修正最多10分钟，同一错误连续出现会结束这一轮；手动重试可开启下一轮。还可免费重新校验已保存响应，或显式改用本地规则生成架构与任务。模型请求及私有回执仍待核对时，页面会说明等待原因。一个项目的当前需求版本同一时间只允许一个执行中、暂停或等待审阅的运行。

## 独立测试提案

已有测试定义也可在该面板展开“导入已有测试定义（不调用模型）”，填写JSON和依据后保存为人工草稿，再单独审阅、认可。每次运行最多20份人工定义，不消耗或退还模型次数；来源与0模型请求明确展示，原模型失败和费用保留。未知请求、旧规划、在途检查点及编码后冻结仍会阻止导入；保存定义不表示软件通过。

规格与计划均确认、工程设计有效且模型配置可用时，可在“代码与验收”展开“独立测试提案（尚未运行）”。先核对模型与预算并勾选，再生成HTTP测试定义；每个运行最多3次尝试，每次最多60秒。生成会调用模型，查看、修改、审阅不调用模型。可以编辑定义并填写依据、驳回或认可；驳回后必须实际修改，认可只绑定当前版本。

**认可定义不表示运行过测试。** 新提案可以同时包含HTTP与浏览器步骤；认可后才可在“按当前规划开发”核对预算并启动多文件编码。编码前冻结定义，候选经自检、独立HTTP/Edge及模型Review，失败限次修复；只在当前同版本完整通过后下载源码。只有HTTP的旧定义仍可审阅，不能启动该路径。此新增路径正在完成集成及业务验证，不代表复杂业务平台全部完成，当前证据见[完整目标台账](docs/tasks/full-goal-completion.md)。

原需求换版后旧定义只读；生成、编码或状态待核对时，可以保存需求草稿，但不能应用需求或删除项目。私有模型回执仅留本机，不进入规划文档包。已有正常停止的当前规划模型候选，可明确同意预算后“保留代码并修复”：核对服务自有Git/原始回执，保留所有历史阻塞义务，在新工作区重新验收，不继承原通过。未知停止、源码或回执不一致时拒绝收费修复。

`npm run planned:check -- --fixture`免费检查隔离执行与真实Edge基础（诊断，不计软件通过）；`--model`会真实请求编码及Review。已有本基准来源可用`--model --source 报告路径`限定一次编码及一次Review修复。`npm run planned:verify -- --archive ZIP路径`免费重新运行普通源码包内定义的 HTTP 与 Edge；它不重新确认历史Review，也不会授予当前软件完成状态。报告保存在本地`output/`。

复核命令末尾加 `--inspect` 可检查源码包结构和版本绑定。演进包额外验证迁移配方及原快照引用，旧数据需由平台持有并批准的原快照复验。加 `--cold-start` 可在空库检查包内已批准的创建用例和重启读回。诊断报告会给出本机临时文件位置。

已结束同版本交付恢复正在独立验收：真实通过时原子封存，重启后核对审批、Git、原回执、代码及策略，才可恢复该历史源码下载；不会把普通JSON当新验收或给旧记录补签。在途未知状态仍待协调。`npm run planned:recovery -- --fixture`免费运行真实隔离/Edge诊断及私有凭据位置拒读写，证明诊断不封存；`--model`使用真实编码/Review并核对两次关闭重启下载，最多3次编码+3次Review及10分钟。该命令的规格、工程和测试定义是明确固定的公开夹具，不测试真实PM规划质量；整个基准使用独立本地数据和随机负责人登录，不改现有项目。

## 全栈执行验证入口

`npm run web:check -- --model`会真实调用模型生成固定`library-web-v1`图书借阅Web项目，产生正常用量；默认最多3轮编码、3次独立Review，共10分钟。它使用已有服务端LLM配置，以及本地`EXECUTION_SANDBOX_EXE`指向的Windows MXC程序；需要Node.js 22.21+和Microsoft Edge，缺少保护或浏览器时明确失败。

模型只能提出允许路径内的多文件文本，平台保护启动外壳和验收器。候选固定Git版本后，先自检，再分别运行18项HTTP/SQLite检查、21项真实浏览器检查及独立Review；新候选重新检查。数据库查询也在有预算的独立MXC进程中进行。生成的应用没有外部网络，源码只读，数据仅写工作区临时目录。

固定参考项目曾完成一次真实模型正向验收：原模型提交`5dc88cd`在当时规则下，HTTP/SQLite自检18项、独立HTTP/SQLite18项、真实Edge浏览器21项全部通过，新Review无阻塞问题。这是历史版本证据，后续规则或提交变化必须重新检查。当前网页候选的真实进展以[STATUS](docs/STATUS.md)为准，失败和阻塞记录不会被历史通过覆盖。当前尚不支持从网页任意需求自动执行、已有业务代码的需求变更、多Worker或完整后台恢复。原纯函数`execution:check`入口继续保留。

当前固定参考的真实修复提交`73020f7`已完成正式零编码复验、网页实际预览借还及源码下载。下载包另经干净副本18项HTTP/数据库和21项Edge检查，以及离线安装、npm start、借还/登出与正常停止；3项非阻塞审查建议保留。旧失败没有覆盖。软件范围仍以明确选择的图书借阅参考契约为准，不能用它宣称任意上传需求已实现。

可信控制器可使用`node scripts/recheck-web.mjs --record <绝对execution.json>`只读核对已有模型候选；同时指定`--run --model-review`才实际重新验收并产生Review用量。复验重新执行全部检查，保留原提交和原报告，不沿用旧通过结论。来源必须是本地控制器拥有、正常停止且源码及私有模型回执完整的执行记录；不能直接提交客户端报告或ZIP声明。

`npm run web:verify -- --archive <源码ZIP路径>`不调用模型，对当前保护外壳生成的交付包核对完整性，并在干净副本重新执行固定HTTP/数据库及浏览器检查。包内历史通过声明不作为可信结论；该命令的`checks_passed`也不等于获得新的模型Review。首个实际源码包已完成18+21项新检查，以及干净目录安装、保护启动和浏览器登录、借阅、归还；启动服务已停止。

源码交付仅接受当前候选的完整同版本结论，输出保护外壳、源码、需求/规格/计划及净化报告。网页“下载文档包”与“下载已验收源码”分别对应规划和软件；源码包注明固定参考契约与关联上传规划的范围，不能据此宣称上传业务全部实现。通过前不生成成功软件交付结论。实际证据见[持续任务记录](docs/tasks/platform-completion.md)。

网页执行生命周期使用`data/executions/service.sqlite`及其下独立工作区保存；原规划JSON继续保留。服务目录只允许一个控制器，重启后先将未确认的执行/预览标为待核对，不自动重跑或声称进程已死。当前仍是单机控制器，不具备正式多Worker恢复；通用测试模型和事务任务库已单独验证，尚未用于这条固定参考执行。

## 本地规则和模型模式

本地规则模式无需密钥，也不会请求外部模型。它按章节区分目标、角色、功能、约束、验收场景和待确认问题，再从功能与约束生成带原文引用的开发任务。全局验收场景保留在规格和集成验证中，待确认范围不会自动变成承诺实现的功能。若文档只有角色操作描述，会将其作为功能候选。未在原文明确的技术栈、工期和负责人保留为待确认项。该模式适合观察流程和形成初稿；长段落中的多个行为可能需要继续拆分。

新版模型模式使用兼容Chat Completions的服务整理规格；规格确认后，再由一次共享工程设计请求生成实体、接口、页面及带输入/输出/文件范围的任务。工程设计不设调用次数上限，单次最多60秒、每运行总时长最多10分钟；自动修正会在通过、相同错误重复、总时长用尽或页面停止时结束。页面在操作前显示该时间预算；错误不会被静默回退成本地规则，只有用户显式选择本地兜底才使用确定性规则。结果仍须审阅，结构覆盖不能证明业务充分或代码完成。已有local/v1按旧规则兼容。若要使用，复制`.env.example`为`.env`，填写服务端配置：

```dotenv
LLM_BASE_URL=https://your-model-service.example/v1
LLM_API_KEY=填写服务提供方的密钥
LLM_MODEL=填写该服务实际支持的模型名称
```

### 使用 DeepSeek

项目配置示例已按 2026 年 11 月 10 日的 [DeepSeek 官方接口说明](https://api-docs.deepseek.com/) 设置为：

```dotenv
LLM_BASE_URL=https://api.deepseek.com
LLM_API_KEY=在本地填写自己的密钥
LLM_MODEL=deepseek-flash
LLM_JSON_MODE=1
LLM_THINKING=disabled
LLM_MAX_TOKENS=16384
LLM_TIMEOUT_MS=120000
```

在 [DeepSeek 开放平台](https://platform.deepseek.com/) 创建 API Key，只在本地 `.env` 填写。该文件由 Git 忽略；前端和导出文件不会接收密钥。`deepseek-v4-pro` 也可通过修改模型名使用，模型可用性以服务提供方当前说明为准。

执行 `npm run model:check`，会真实调用模型分析一条简短需求，并检查 JSON 结构和原文引用；调用会产生正常 API 用量，终端不会输出密钥。修改 `.env` 后重启服务并刷新前端，即可选择模型模式。

非思考模式用于先验证需求整理链路。`LLM_THINKING` 是 DeepSeek 扩展参数，切换其他兼容服务时应按其文档设置或留空。输出被截断时会明确报错，不把不完整规格当成成功结果。[JSON 输出](https://api-docs.deepseek.com/guides/json_mode/)、[思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)。

`LLM_BASE_URL` 是基础地址，不包含 `/chat/completions`。本地 `localhost`、`127.0.0.1` 模型服务可以不填密钥；远程服务需要密钥。服务启动后会显示模型是否已配置，修改配置后重启服务。

模型收到的是需求文档内容。系统检查模型返回的结构、验收条件和原文引用；无法在原始需求中找到的引用会被拒绝。接口错误不会自动伪装成本地规则成功。密钥只由后端读取，不进入前端配置或导出文档。

| 配置 | 默认值与作用 |
| --- | --- |
| `PORT` | `4317`，本地服务端口。 |
| `HOST` | `127.0.0.1`，默认只在本机访问。 |
| `DATA_DIR` | 项目目录下的 `data`，项目与运行记录保存位置。 |
| `WORKFLOW_STEP_DELAY_MS` | `350`，方便观察阶段变化的演示间隔；设为 `0` 可去除间隔。 |
| `LLM_JSON_MODE` | `1`，要求服务返回 JSON 对象；服务不支持该参数时可设为 `0`，仍须返回有效 JSON 规格。 |
| `LLM_THINKING` | 默认不发送；DeepSeek 示例配置为 `disabled`，可设 `enabled`。其他服务不支持时留空。 |
| `LLM_MAX_TOKENS` | 默认不发送；DeepSeek 示例配置为 `16384`，限制单次输出长度。 |
| `LLM_TIMEOUT_MS` | `90000`，模型请求超时，程序限制在 1 至 120 秒之间。 |

## 输入与数据保存

支持 UTF-8 `.md`、`.txt` 以及标准 `.docx`。DOCX 提取正文文本；图片、扫描件、页眉页脚、批注等内容不作为需求来源。首版不接受 PDF 或旧版 `.doc`。

JSON 请求上限为 6 MB，DOCX 文件上限为 3 MB，提取后的文本上限为 100000 字符。本地规则与模型规格都最多保留 80 条需求；超过上限应按模块拆分，程序不会静默丢弃后续内容。

项目记录以 `data/<project-id>.json` 原子写入，包含原始文本、运行快照、状态、尝试记录、日志和产物。`data/` 与 `.env` 不进入版本控制。导出 ZIP 是对当前运行产物的下载，不会修改工作目录中的目标软件。

服务重启后，已完成和等待审阅的运行可以继续查看。执行中或暂停的运行会标为中断失败，成功产物保留，用户通过重试继续。首版不提供多用户身份认证、分布式调度和运行取消，适合本机课程演示。

## 受控编码试验

本轮新增一个独立程序入口，用固定图书借阅模块验证“模型提出改动 → 真实文件写入 → 固定代码版本 → 受限环境执行 → 平台判断业务结果”。允许修改的文件只有 `src/borrow.mjs`，平台掌握验收规则；每次调用保存独立工作区、提交、差异、命令结果、检查清单及失败历史。

当前执行后端只支持已经具备 Windows MXC 受限执行能力的现代 Codex CLI。先在本地 `.env` 设置 `EXECUTION_SANDBOX_EXE` 为该原生程序的绝对路径。旧版 npm CLI 的 `workspace-write` 标签不足以证明 Windows 隔离；预检必须实际证明工作区外读写和网络被拒绝。未配置、不支持或预检失败时停止，不自动安装系统组件，也不退回宿主运行。

```powershell
# 不调用模型：使用可信固定候选验证本机执行环境。
npm run execution:check -- --fixture
# 真实编码与独立Review：沿用 LLM_* 配置，编码和Review各最多2次请求，会产生正常用量。
npm run execution:check -- --model
```

不带参数只显示用法，不产生模型调用。总时长上限为180秒；编码与Review共用该时长及用量记录，最多4次模型请求。候选代码每次执行上限15秒，模型响应、代码和进程输出均有限额。按 Ctrl+C 请求停止，入口等待两方检查结束或停止确认后退出。目标程序不会继承平台模型密钥，检查期间候选目录只读且禁止网络。

编码自检通过后，平台从Git候选对象读取固定源码，分别建立测试与Review副本。独立测试服务重新执行固定用例；Review模型只读取规格、源码和历史问题，不读取测试结论。两方并行检查同一提交，候选或副本变化、缺少结论、服务错误、测试失败或阻塞问题未关闭，都不能放行。修复形成新提交后两方重新检查，旧结果仅保留历史。Review必须明确复验历史阻塞问题，编码器不能自行关闭。

记录保存在 `output/executions/`，由 Git 忽略。真实两方通过时状态为 `accepted`、`acceptanceStatus: passed`，仅表示当前固定纯函数任务通过。`--fixture`使用可信候选与模拟Review，显示`diagnostic_passed`和`taskAccepted: false`，不产生模型调用。底层未提供Review的兼容调用仍只执行自检，结果为`executed/not_reviewed`，不能作为任务验收完成。

目前测试侧为平台固定验证服务，尚未实现测试模型自主生成用例。浏览器规划任务、依赖安装、任意仓库、全栈软件及集成交付尚未接入；本轮固定任务门禁不能作为完整软件通过验收的结论。

该任务限同步纯函数，候选在独立JavaScript上下文执行，无法使用Node进程、文件、网络或导入依赖。可信观察器不使用候选可修改的JSON函数，不执行返回值的getter/toJSON/thenable。MXC仍是系统执行边界；JavaScript上下文不代替系统隔离。验收清单同时记录用例和观察器哈希，执行记录附平台源码标识与Node版本。

## 常见问题

- **端口被占用**：在 `.env` 调整 `PORT`，重启后使用终端打印的新地址。
- **模型选项不可用**：先用本地规则模式；如需模型模式，检查三个 `LLM_*` 配置及服务端日志。
- **出现“等待审阅”**：这是确认导出的正常停点。查看 `task.md` 后点击“确认并导出”。
- **失败后没有立即出现重试按钮**：等待已启动的独立分支结束，运行进入失败状态后再重试。
- **本地任务粒度较粗**：在原始需求中使用清晰的功能标题和条目，或启用模型模式整理后人工确认。

接口实现参考：[Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)；测试工具参考：[Node.js Test runner](https://nodejs.org/api/test.html)。

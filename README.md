# Taskflow 需求编排台

把软件需求文档转换为可审阅的设计规格、架构建议和 `task.md`，通过前端展示每个规划阶段的依赖、状态、日志与文档产物。

这是一个可以本地运行的课程项目原型，包含真实的后端调度与持久化。它生成后续软件开发计划，编码任务仍由开发团队或另行接入的执行器完成。首版不会执行需求文档中的命令，也不会自动修改目标软件仓库。

## 启动

安装 Node.js 22 或以上版本，在项目目录执行：

```powershell
node --version
npm start
```

浏览器打开 [本地工作台](http://127.0.0.1:4317)。Windows 下也可以双击 `start.cmd` 启动。停止服务时，在启动终端按 `Ctrl+C`。

项目没有第三方运行依赖，无需先执行 `npm install`。修改服务端代码时可用 `npm run dev` 启动监视模式；修改前端静态文件后刷新页面即可。

## 演示一条完整流程

1. 点击“新建项目”，再点击“载入示例”，或上传自己的 `.md`、`.txt`、`.docx` 软件需求文档。也可以直接粘贴需求文本。
2. 点击“创建项目”。选择本地规则模式，点击“开始编排”。
3. 在工作流图中观察读取需求、整理规格、设计架构和拆解任务等阶段。架构与任务拆解在规格完成后并行执行。
4. 点击阶段查看日志，打开已生成的 `spec.md`、`architecture.md`、`task.md` 和检查报告。开发任务视图展示另一张图：目标软件的候选任务及其依赖。
5. 运行停在“等待审阅”时，核对原文引用、任务粒度、验收条件与未确定项。可以填写审阅意见，再点击“确认并导出”。
6. 导出阶段完成后，下载单份 Markdown 或完整 ZIP 文档包。切换运行记录可以查看历史输入与产物。

规划阶段的“成功”表示该阶段已生成并校验相应计划产物。`task.md` 中的开发任务初始状态是待开发，两种进度在界面与文档中分别呈现。

示例文件：

- [工单协作系统](examples/issue-tracker.md)：登录、创建、分派、状态流转、评论和筛选。
- [校园图书借阅系统](examples/library-system.md)：馆藏查询、借还、库存约束和管理权限。

## 暂停与失败恢复

暂停在阶段边界生效：已经启动的阶段会完成，后续阶段暂不启动。点击恢复后，编排器重新检查依赖并继续执行。

可在演示选项中给任务拆解、架构设计或检查阶段注入一次故障。例如让任务拆解首次失败：架构分支仍可完成，下游检查与导出被阻塞。运行结束后，选择失败阶段重试；成功分支不会重新执行，失败阶段的尝试次数和历史记录仍可查看。演示故障会明确记录在日志中。

真实的输入问题需要修改需求并新建项目；模型配置等问题可在修正服务配置后重试。重复相同输入不能保证解决错误。一个项目同一时间只允许一个执行中、暂停或等待审阅的运行。

## 生成的文件

| 文件 | 内容 |
| --- | --- |
| `requirements.md` | 导出包中的需求文本快照。DOCX 输入保存为提取后的正文。 |
| `spec.md` | 项目目标、编号需求、原文引用、约束、验收建议及待确认事项。 |
| `architecture.md` | 模块职责、候选领域对象、技术边界和接口确认清单。 |
| `task.md` | 开发任务、前置依赖、需求来源、建议修改位置和验收条件。 |
| `review.md` | 依赖合法性、任务验收条件和需求映射检查结果。 |
| `handoff.md` | 审阅意见、文档清单与后续开发安排。 |
| `plan.json` | 可供其他工具读取的结构化规格、任务和检查结果。 |

结构检查通过表示任务图和需求映射满足程序规则。业务含义、真正的跨功能依赖和验收充分性仍须人工审阅。

## 本地规则和模型模式

本地规则模式无需密钥，也不会请求外部模型。它按章节区分目标、角色、功能、约束、验收场景和待确认问题，再从功能与约束生成带原文引用的开发任务。全局验收场景保留在规格和集成验证中，待确认范围不会自动变成承诺实现的功能。若文档只有角色操作描述，会将其作为功能候选。未在原文明确的技术栈、工期和负责人保留为待确认项。该模式适合观察流程和形成初稿；长段落中的多个行为可能需要继续拆分。

模型模式使用兼容 Chat Completions 的服务对需求进行语义整理，随后共用同一套任务生成、结构校验和编排逻辑。若要使用，复制 `.env.example` 为 `.env`，填写服务端配置：

```dotenv
LLM_BASE_URL=https://your-model-service.example/v1
LLM_API_KEY=填写服务提供方的密钥
LLM_MODEL=填写该服务实际支持的模型名称
```

`LLM_BASE_URL` 是基础地址，不包含 `/chat/completions`。本地 `localhost`、`127.0.0.1` 模型服务可以不填密钥；远程服务需要密钥。服务启动后会显示模型是否已配置，修改配置后重启服务。

模型收到的是需求文档内容。系统检查模型返回的结构、验收条件和原文引用；无法在原始需求中找到的引用会被拒绝。接口错误不会自动伪装成本地规则成功。密钥只由后端读取，不进入前端配置或导出文档。

| 配置 | 默认值与作用 |
| --- | --- |
| `PORT` | `4317`，本地服务端口。 |
| `HOST` | `127.0.0.1`，默认只在本机访问。 |
| `DATA_DIR` | 项目目录下的 `data`，项目与运行记录保存位置。 |
| `WORKFLOW_STEP_DELAY_MS` | `350`，方便观察阶段变化的演示间隔；设为 `0` 可去除间隔。 |
| `LLM_JSON_MODE` | `1`，要求服务返回 JSON 对象；服务不支持该参数时可设为 `0`，仍须返回有效 JSON 规格。 |
| `LLM_TIMEOUT_MS` | `90000`，模型请求超时，程序限制在 1 至 120 秒之间。 |

## 输入与数据保存

支持 UTF-8 `.md`、`.txt` 以及标准 `.docx`。DOCX 提取正文文本；图片、扫描件、页眉页脚、批注等内容不作为需求来源。首版不接受 PDF 或旧版 `.doc`。

JSON 请求上限为 6 MB，DOCX 文件上限为 3 MB，提取后的文本上限为 100000 字符。本地规则与模型规格都最多保留 80 条需求；超过上限应按模块拆分，程序不会静默丢弃后续内容。

项目记录以 `data/<project-id>.json` 原子写入，包含原始文本、运行快照、状态、尝试记录、日志和产物。`data/` 与 `.env` 不进入版本控制。导出 ZIP 是对当前运行产物的下载，不会修改工作目录中的目标软件。

服务重启后，已完成和等待审阅的运行可以继续查看。执行中或暂停的运行会标为中断失败，成功产物保留，用户通过重试继续。首版不提供多用户身份认证、分布式调度和运行取消，适合本机课程演示。

## 测试和检查

```powershell
npm test
npm run check
```

自动化测试使用 Node.js 自带测试工具，测试数据保存在临时目录，不修改用户项目数据。覆盖规划器原文追踪与任务覆盖、DAG 校验、文档文本转义、模型适配器模拟响应，以及后端编排和文件接口。

模型适配器测试通过注入模拟响应验证接口格式、输出校验和错误遮蔽，不会调用真实付费服务。使用自己的模型配置后，可再用同一需求验证真实服务的连通性与输出质量。

## 项目结构

```text
public/                 前端工作台与交互图
lib/planner.mjs         规格分析、开发任务生成和文档渲染
lib/orchestrator.mjs    工作流调度、状态推进、审阅门禁和重试
lib/store.mjs           本地项目记录与原子持久化
lib/documents.mjs       文本与 DOCX 输入解析
lib/zip.mjs             导出 ZIP 文档包
server.mjs              HTTP API 和静态文件服务
tests/                  规划器、编排器和接口测试
examples/               两份可导入的软件需求
docs/API.md             请求与数据结构约定
docs/DESIGN.md          当前软件开发场景的设计说明
```

目录中的 Word 讨论稿为早期 CSV 演示方案，作为讨论历史保留。当前项目以 [软件需求编排设计](docs/DESIGN.md) 和实际接口为准。

## 常见问题

- **端口被占用**：在 `.env` 调整 `PORT`，重启后使用终端打印的新地址。
- **模型选项不可用**：先用本地规则模式；如需模型模式，检查三个 `LLM_*` 配置及服务端日志。
- **出现“等待审阅”**：这是确认导出的正常停点。查看 `task.md` 后点击“确认并导出”。
- **失败后没有立即出现重试按钮**：等待已启动的独立分支结束，运行进入失败状态后再重试。
- **本地任务粒度较粗**：在原始需求中使用清晰的功能标题和条目，或启用模型模式整理后人工确认。

接口实现参考：[Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)；测试工具参考：[Node.js Test runner](https://nodejs.org/api/test.html)。

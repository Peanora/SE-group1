# 当前规划原型实现说明

`frontend/` 下的 React 和 TypeScript 页面由 Vite 编译到 `public/ui/`。项目工作台、API 服务、Agent 角色、团队账号和 Factory 外壳从同一 Node 服务加载各自入口。工作台使用项目与运行记录组织规划、任务、需求变更和验收，并复用现有面板请求、版本检查及轮询。

项目页在侧栏选择项目和进入设置，在主区标题旁选择运行。下方展示运行概况、流程与操作以及工作区标签。开发计划可在依赖图与计划清单间切换，清单和任务详情共用当前运行的选择及版本。运行历史和 Factory 回程按项目与运行编号读取。

## Factory 工作流

Taskflow 项目页启动固定版本 Factory 进程，浏览器从该进程的回环地址直接打开完整原版页面。原生运行时提供 HTTP、会话 SSE 和终端 WebSocket。规格交接预先记录 Taskflow 运行、规格版本和工作区身份，再关联原生工作流。重启后从对应仓库读取原生状态、集成分支和提交。Taskflow 自有验收与源码交付使用自身的独立门禁。[功能对照](FACTORY_WORKBENCH.md)。

## 开发计划与任务画布

规格确认后，新版规划按可验收功能拆解模块，产出模块名、所属功能板块、职责、输入、输出、验收和直接前置。工程模型规划提供模块与代码写入范围。本地规则从功能标题和命名条目提取模块，根据已确认规格的显式需求引用连线。架构说明、任务文档、`run.tasks` 和导出的计划使用同一版本。一次计划修订可更改模块名与板块。

画布把功能板块画作横向泳道，依赖深度决定列，每个模块占一张卡。分叉、汇合与关键检查点标在有关卡片或连线上。点开模块详情可看执行步骤，运行证据按同一候选展示。相同深度支持上下换位，同一泳道内交换两个模块，跨泳道则交换板块顺序。顺序按运行、版本、草稿保存在当前浏览器会话。只有编辑模块右侧出口到后继左侧入口的连线并保存才会修订计划。

多模块工程计划首次生成即以 `dependencyExecution: true` 版本参与审批和导出。板块名称不参与派发条件。超出执行器范围的工程图仍可审阅和导出，正式开发需要通过逐任务准入及联合清单门禁。已确认的历史计划保留原版本和执行策略。

负责人可在画布编辑直接依赖并保存计划修订。按图运行标记参与计划内容哈希。当前正式执行需要 2 至 8 个任务、一项基础入口、一项最终集成、精确写入范围、需求追踪和逐任务联合验收清单。`lib/planned-task-executor.mjs` 在计划和验收定义确认后，按 SQLite 中的直接前置完成状态补充派发。候选通过同版自检、独立 HTTP、Edge 和 Review 后，只有 Git 集成和可信状态提交成功才释放后继。以更早基础启动的候选需另行核对写入冲突及合并结果。失败停止新派发，已启动任务继续核对终止状态与用量。真实画布依据当前执行版本显示已通过、待集成、待派发或未通过。最终集成使用整个项目的验收清单。

版本条读取规格与计划的内容版本和审批。在待确认计划上进入原规划审阅，当前版计划确认并导出后链接到原验收准备工作区。修订预览明确区分于保存版本。模拟运行切换到冻结的计划定义与后端状态，历史记录按既有只读约束展示。

真实逐任务开发可以在收费确认前选择执行配方。服务器将编号映射为单项或双项并发上限，随执行行及持久 Worker 的授权冻结。切换配方需要重新勾选用量确认。当前依赖、写入范围、时限、审核及每角色调用上限仍由该计划和联合清单决定。

## 多 Agent 规格评审

手动 v2 规划的规格停点显式启用六节点会议，复用 ProjectStore、项目操作锁、规格版本、问题会话与双确认。新会议用同一议题约束各席独立提案，随后交叉质疑固定的提案及同版上下文，再把缺项、跨条款冲突和业务裁决分流。`lib/specification-meeting.mjs` 管理版本、回执、返工和联合包。`public/specification-meeting.js` 可从分流项定位规格编辑或进入人工裁决。实际修订形成新版，原阻塞由原席复核。人工联合确认后才进入架构与任务。历史轮次沿用各自的放行规则。

可使用默认离线夹具，也可显式启用已配置的模型服务。交付入口独立于定向会议，定义清单供后续验证使用。[接口、恢复与演示](SPECIFICATION_MEETING.md)

## 自动交付运行

自动入口以一次模型用量确认为起点，在项目存档记录本次运行的授权配置版本、阶段以及清单和开发记录编号。各阶段继续使用规格引用校验、工程与计划验收、独立测试清单验证和开发服务的实际交付门禁。自动审批使用版本绑定并记录依据，原逐步审阅入口仍可单独使用。

前端九步流程显示控制器的当前阶段和后端证据。需要补清的业务问题复用版本化问答，提交后同一运行继续。对已可靠停下的模型格式问题和可确定的清单缺陷按既有规则尝试修复。代码候选仍由独立 Worker 逐版运行真实检查并处理审查阻塞。只有当前执行开放源码下载时，自动运行才发布完成。新运行在清单和开发派发之前持久化意图，重启后重新授权并核对唯一的同版本记录。证据不足时保留待核对的用量和原始状态。流程图同时显示规格、工程、验收准备和研发四阶段的已确认用量和冻结报价估算。

自动清单返工从当前计划已结束的阶段提取有界诊断，核对缺失的 HTTP 覆盖、页面结果断言、步骤依赖与响应格式。普通计划重提联合清单。至少 16 项需求且有确认页面的计划先生成接口检查，保存可核对的部分，需要时仅补缺项，再请求独立浏览器步骤。每次派发保留原回执和费用。自动批准前核对原联合规则与已确认页面的可观察断言。生成的 HTTP 需求覆盖要求对应已确认的同方法接口或页面。手动阶段用尽时，已有有效接口草案可分别确认一次缺项补齐和一次浏览器生成，重启后从最新可用的回执继续。业务验收继续由独立运行与同候选审查决定。

## 网页多角色与 API 配置

导航提供「Agent 角色」和「API 服务」两个独立页面。API 服务页面用列表和抽屉管理地址、模型与密钥。Agent 角色页面仅为规格、工程规划、测试提案、编码和审查分配已保存的服务。两个页面使用同一配置版本，各自提交本页修改与读取时的其他字段。服务可以共用，`env` 继续使用 `.env` 环境默认配置。

保存与应用通过本机后端接口执行，整体版本比较防止多页面覆盖。密钥不回填、不进浏览器存储，服务端加密保存在私有数据目录。原生模型适配器接收配置快照，规划逐次调用取配置，开发按一次执行冻结编码/审查双路配置，Worker 恢复核对双路配置版本。已有调用和检查结果不因配置保存而改变。付费请求仍由原有用户操作和预算门禁发起。

已确认的专用登录修订优先尝试接续旧认可清单。工作台确认计划版本、旧浏览器首次失败和已确认的登录表单、测试账号后，补独立登录前置，并保留原 HTTP 和浏览器检查。需要连续建号时，每次提交后先核对已填账号清空，再读取状态。自动保存结果为当前计划的待审阅草案。草案确认后才能继续开发。没有足够证据时，主界面直接显示具体原因及可用的草案恢复入口。

## 项目全流程与任务修订

首页提供可展开的九步流程摘要，显示当前阶段及已完成数量。需求输入节点可打开新建对话框，已有项目的节点定位到对应工作区。规划分支图和模块依赖图保留各自的真实依赖与运行证据。

确认模型工程计划后，从验收节点核对预算并显式发起清单生成。可确定的草案故障在原请求之后自动生成待审阅记录。用户确认清单后可以开始开发。流程图通过实际执行状态显示编码、自检和独立审查进度以及返工次数。

验收节点在当前计划有可用联合清单时提示待确认，各份清单和失败记录可在验收面板切换查看。可确定的失败可从现有模型回复恢复草案。软件通过同版本完整检查后，交付节点定位到本地预览、停止预览及源码下载。

全流程概览从当前项目与所选规划运行的记录读取状态。需求、规格、两次确认和计划使用规划状态，验收准备使用绑定本计划的联合定义，编码、测试与审查、交付使用当前版本的开发执行结果。点击对应节点会定位工作区和实际内容。代码区把验收准备与付费编码分成连续操作，参考项目和其他工具收在单独入口。验收通过前，交付保持等待状态。

「需求与功能」直接展开编辑工作区。点击流程节点可定位生效正文、草稿预览、变更差异和重新规划入口。版本侧栏可选历史记录，选择记录不会覆盖正在编辑的需求。应用需在共同安全检查点成功并经读取核对，之后才能从该版本重新规划。

「代码与验收」提供可点击的验收准备、编写代码、测试与审查、交付步骤。逐任务执行显示真实依赖画布，选择任务可查看前置依赖、下游影响、固定候选和检查证据。整体执行按实际候选展示编码、自检、接口、浏览器和审查结果。历史矩阵只展示对应尝试和提交留存的数据，未知结果不当作通过。窄屏将依赖节点按顺序排列，保留选择和证据。

再次进入「代码与验收」默认打开交付总览。总览从所选运行的规划确认和正式候选记录整理卡点、版本链及检查计数。验收清单、候选与证据、本机版本、参考实验各有标签。流程节点和失败通知进入相应标签并定位操作。本机版本读取已核对的本机登记、备份和迁移决策。参考实验继续使用显式范围授权，自己的运行无法发布正式候选的验收结果。

代码审查按固定候选的实际源码行和已确认规格检查，重复新意见会被拒绝并保留诊断。每次返工产生新提交后，全部历史阻塞问题按原编号重新复核，当前提交的关闭结果记录 `checkedCommit`。审查未完成或仍有阻塞时，候选停在未通过状态。接口和工作台 Review 详情保留逐版本问题及复核历史，同一候选格式重试成功后也保留前次拒绝原因。预约队首独立演示和验证说明见[李文宇的代码审查交接](tasks/project-code-review.md)。

「执行角色进度」使用开发执行列表中的当前阶段、候选提交、模型调用和检查记录。分任务执行按任务和尝试编号读取对应证据，支持查看不同任务同时处于测试和审查的情况。已记录的测试失败优先显示，前置自检失败时显示本轮未开始测试。测试详情包含当前候选的测试进程错误，即使尚未生成逐项检查结果。返工期间，详情标记最近固定的上一轮提交，当前角色等待新候选，暂不可用的证据按钮保留键盘焦点。读取失败时提示刷新核对。角色进度用于查看和跳转证据，预览、源码下载和执行动作继续由原有服务端许可控制。

拥有编辑权限的用户可在已确认计划上打开任务编辑器。保存实际更改会创建计划修订，旧计划、确认、验收和代码记录按原版本保留。新计划完成依赖及覆盖检查后重新等待确认。开发、测试提案、预览或未知状态未结束时，保存会被项目检查点拒绝，编辑草稿保留。

验收清单生成失败时，问题区展示校验原因及漏测需求。通过文件完整性和当前计划绑定核对后，负责人可以载入已有步骤继续修改。若只涉及可确定的前置依赖或无效的可选任务分组，页面可直接保存修复草案。此路径重新执行原完整校验，保留全部检查和预期结果。旧失败保留为历史，新的清单仍须人工认可。

已知的纯入口页覆盖遗漏可补访问检查。清单复用可重复列表条目作为唯一总数元素时，临时载入草案可拆开两者；如隔离的首次加载用例后紧接普通会话的创建结果，还会补该普通会话的填写与提交。原期望、原报告与已冻结清单保留。当前仍有歧义的业务预期由负责人在新版本确认。

2026-11-18新候选将当前确认规格中每条需求的标题、完整正文与验收条件，一并交给整体、逐任务及Worker编码/Review，不再只有概要和工程契约。历史完整响应但异常finish的失败调用保留原回执和费用；新候选的实际coding与当前Review仍必须正常stop，未知远端、缺失或不一致证据仍拒绝。该候选正独立验收，不能以此说明复杂业务已经通过。较早阶段描述以STATUS最新固定版本及证据为准。

## 最新集成候选（2026-11-18）

F07规划预览/脱敏实际命令/真实依赖图已接服务和网页，独立固定副本通过；生命周期原P2已由两组非作者复核。F05 core/source私有跨版seed与真实旧数据迁移副本通过216固定副本的Test与Review；新本机业务版本、精确迁移审批/整体开发、成对激活/受限回滚已接候选服务和路由，新网页五类交互问题修后独立Edge25/25。F08正常研发已增加持久审批/outbox/独立Worker/重连/新用途封签与已知停止费用结算，作者14文件94/94；完整产品的同版独立验收继续进行。

整体跨版本演进复用持久 Worker 的授权、原预算、接回和签名结果。预留事务绑定批准的演进意图。Worker 重查原批准、启动关联和已停止的本机发布，使用只读原数据账本生成各阶段独立迁移副本。验证完成后，API 对照签名、固定源码、作业迁移账本和原始数据回执发布。原数据库保留在自己的发布版本，迁移文件属于作业私有目录。已有进程内记录仍按原身份核对。

源码检查目录与owned业务运行目录明确分离。快照指向后者，所有测试副本独立迁移，旧mutable业务库不进入模型反馈；预览与测试库不能自动当业务数据。普通源码包只保留脱敏验收与演进摘要，不含数据库/私有路径。新本机激活是明确操作，不因accepted或下载自动替换用户数据，也不部署公网。

当前仍有限制：演进多任务scope未接时拒绝，source/seed执行尚不通过持久Worker；激活后历史演进源码资格与旧数据live门禁需单独闭合；有效暂停任务检查点的故障续跑尚未接。串行HTTP handler是当前全链隔离设计，可验同时请求下的结果一致性，不宣传handler真正重叠执行。各项能力以当前固定代码与实际证据为准，下方较早“尚未接线”保留为阶段记录。

## 真实逐任务候选（2026-11-18，继续集成验收）

批准联合定义可绑定完整任务集合及逐任务HTTP/浏览器范围，可信编译器补齐原步骤依赖但不修改期望。无分组旧定义保持整体编码；有分组时新增真实认领/租约和独立Git克隆，最多两项就绪任务并行，主控制器独占集成写入。任务的局部同版本HTTP/Edge/Review及来源核对均通过后，才在实际Git合并后完成任务、释放下游；最终全依赖末项使用完整父清单重新验收。代码复用许可、局部任务通过、最终软件通过与历史交付恢复分别处理，不能互相替代。

当前修复候选加入同计划的精确上游返工：只有完整集成原始对象的私有能力可触发，且只自动处理所有未关闭阻塞均归同一上游负责者的情况。任务库按已确认依赖事务重开根及下游；旧尝试、费用和阻塞历史保留，晚到旧完成不能再声称 current。返工上限一次，累计次数、时间和全图预算不清零；多负责者或混合阻塞保守失败。每任务 history 和封存交付保留全过程。真实第二次基准已经证明并行及合并，但最终真实审查阻塞未关而失败；本修复仍在独立固定组合检查，详见 [集成返工](tasks/planned-integration-rework.md)。

## 规划驱动的真实候选路径（持续验收中）

## 模块和数据流

前端负责输入、模式选择、运行控制、依赖图、日志和文档预览。HTTP 服务验证输入与状态，再调用编排器或读取已发布产物。规划器只返回结构化数据和文本；执行器不会执行用户文档中的代码。

| 模块 | 职责 | 主要输入输出 |
| --- | --- | --- |
| 文档解析 | 接收 UTF-8 文本或提取 DOCX 正文，限制文件与文本大小。 | 上传内容 → 需求文本 |
| 规划器 | 提取规格、生成开发任务、渲染文档、检查覆盖与依赖。 | 需求文本 → 规格、任务、Markdown |
| 编排器 | 按依赖启动阶段，推进状态，处理审阅、暂停与重试。 | 运行与操作 → 阶段状态、事件、产物 |
| 本地存储 | 保存项目、不可变需求引用和每次运行记录。 | 项目对象 → 原子写入的 JSON |
| 前端工作台 | 展示规划过程和开发计划，提供可执行的用户操作。 | API 状态 → 图、日志、预览和下载 |

每个项目可以多次运行。一个项目同一时刻只允许一个执行中、暂停或等待审阅的运行，避免用户误将多个活动过程混为一份结果。再次运行创建新的 `run_id`；失败重试沿用当前运行并递增对应阶段的 `attempt`。

## 需求规格和来源

需求解析得到标题、摘要、目标、角色、编号需求、约束、全局验收场景、假设、待确认问题和技术边界。每条编号需求包含描述、验收建议、类别和 `sourceQuote`，下游开发任务通过 `requirementIds` 关联需求。

本地规则模式按章节区分上下文与实现范围。项目背景进入目标，角色单独保留，功能与约束形成编号需求；验收场景进入规格和集成验证，待确认事项留作问题。若没有独立功能章节但角色中包含操作，可将这些操作作为功能候选。该模式适合离线演示和快速初稿，仍不能判断所有业务关系：一段话中的多个行为可能需要继续拆分。未给出的选型、工期和负责人保留为待确认项。

模型模式将文档作为数据发送给配置的Chat Completions兼容服务。规格必须满足结构要求，每个原文引用逐字存在；不满足时失败。新版model规格确认后，架构和任务共享一次有界工程模型请求，生成实体、角色/接口、页面及有输入、输出和精确文件范围的任务。失败不回退规则，完整草案参与计划hash；人工改任务同步草案并重校验，规格回修使下游失效。local及v1仍沿旧规则。草案只证明structural_only，不能代替语义审阅或执行验收。

工程草案失败时页面显示是否有可免费重新校验的已保存回执、剩余模型尝试和下一步。模型把路由参数写成`{recordId}`时，控制器规范化为`:recordId`；常见纯文本ARIA角色别名也会规范化。其他JSON、结构、写入冲突或角色错误不会被静默改写。

草案因JSON或结构校验失败时，平台把具体校验说明反馈给模型。默认不限调用次数，单次最多60秒，每轮自动修正最多10分钟。手动重试可开始新一轮。重复错误、非结构错误、超时或停止会结束本轮。原调用和私有回执保持。也可重新校验已保存草案，或显式改用本地规则后重新进行计划确认。

「查看问题」首轮集中询问影响首版范围或验收的事项。提交后，仅把本轮回答含糊的原题及上次答复带到补答界面。首版未明确的实现细节可记为假设，后续规格不再自动新增问题。引用失败可查看从当前可信回执摘录的草案条目和引用，直接用已有材料重整。旧运行中过时的问题可跳过填答并重新整理，原存档不被重写。

| `pending` | 尚未开始；只有全部前置阶段成功才可运行。 |
| `running` | 已被调度，当前尝试正在执行。 |
| `succeeded` | 执行成功且产物已经发布。 |
| `failed` | 当前尝试失败，保留错误与历史记录。 |
| `blocked` | 前置阶段失败，当前阶段无法继续。 |

编排器最多并行启动两个可运行阶段，因此架构与任务拆解可以并行。在本地模式下，默认增加 350 毫秒阶段观察间隔，便于前端展示变化；配置为零时去除该间隔，调度规则保持一致。

运行状态包括执行中、暂停、等待审阅、成功和失败。所有阶段成功后运行成功；没有可执行或执行中阶段且存在失败或阻塞时运行失败。检查阶段成功后，导出阶段保持待执行，运行进入 `awaiting_review`。仅此状态接受人工确认，审阅意见写入交接文档。

暂停属于阶段边界暂停。已启动阶段允许结束，编排器不再启动后继；恢复后重新检查依赖。停止服务或进程中断不等同于暂停：重启时会把执行中和暂停的运行转为中断失败，以便用户明确选择重试；已完成和等待审阅的记录保持可查看。

## 失败和重试

阶段异常会记录任务、尝试次数、时间和原因，并将尚未执行的后继标为阻塞。独立分支继续执行，待运行结束后才允许重试，避免与尚未完成的分支产生状态冲突。

重试选定的失败节点时，编排器保留成功分支和已发布的产物，重新检查后继的所有依赖。还有其他失败前置时，后继仍不能启动。日志和尝试历史累计保存，便于解释“第一次失败、第二次成功”的过程。

演示选项支持指定阶段首次失败，用于复核分支保留与恢复逻辑。该故障会显示在日志中。原始需求无效、模型配置错误等真实问题仍需修正输入或配置，不能承诺点击重试一定成功。

## 可视化交互

界面包含项目导航、模式和运行选择、规划工作流、开发任务、阶段详情、执行事件和产物预览。所有更改经后端校验，连续点击不能重复启动同一有效操作。

工作流节点配合文字和颜色显示状态。任务详情展示需求来源、依赖、修改位置和验收。事件按递增序号排列，前端轮询合并结果；选择节点、文本输入和审阅意见不能因为刷新而丢失。产物可在发布后单独查看与下载，完整 ZIP 包在确认导出成功后开放。

Markdown 内容作为文本安全渲染，需求中的 HTML 不作为页面代码运行。服务端默认只监听回环地址，密钥仅在服务端读取；需求与产物保存在本地，使用模型模式时需求内容会发送给所配置的服务。

## 首版验收

1. 导入任意一份示例需求，跑通规格、架构、任务、检查和人工导出，得到真实文档。
2. 改用另一份业务需求，规格与任务内容随输入变化，原文引用可逐项查到。
3. 所有需求都有开发任务映射，任务包含依赖和验收，非法图被拒绝。
4. 注入一次任务拆解失败，架构分支保留；重试成功后进入审阅，已成功阶段不重复运行。
5. 暂停后不启动后继，恢复后继续；重复操作被后端拒绝。
6. 刷新页面或重启服务后可查看历史记录；中断的运行有明确失败状态。
7. DOCX 输入提取正文，非法或超限文件有明确提示。
8. 模拟模型输出覆盖合法响应、错误引用和服务错误，真实模型连通性按使用者配置另行验证。

本地单用户运行、固定规划工作流和确定性的任务模板构成首版范围。未来若要自动执行开发任务，需要另外定义仓库访问、执行器、产物检查与失败恢复协议，不能把规划节点成功直接解释为目标软件已完成。

## 当前独立Web执行范围

浏览器工作台继续保留上述规划子流程，并新增与其分开的固定`library-web-v1`代码执行区域；规格和计划均确认后，用户须明确选择参考契约与预算。独立CLI已有多文件生成、Git候选、SQLite受控运行、HTTP/浏览器/模型Review同版本门禁及源码交付；网页复用同一执行器和统一门禁，显示后端事实，不将规划任务图改成已执行任务。首个CLI真实模型候选已通过完整固定业务检查并完成干净目录启动；网页实际模型正向验证的事实另见[VERIFICATION](VERIFICATION.md)。这不是从任意上传需求自动生成复杂项目的通用能力。

生成应用只导出`createApp({databasePath})`及有界请求处理接口；平台固定worker在无网络、源只读的MXC中调用，宿主将随机localhost端口的HTTP转为有界stdio消息。数据库只写当前私有数据目录，验收在独立快照和数据库运行。浏览器会话使用单独Cookie命名空间及来源限制。源码包保护启动外壳在导入可信runtime前检查哈希；不直接在宿主执行生成的应用模块。

已有模型候选可以在不改代码的情况下建立新版本复验记录，完整重跑固定检查和新Review；原提交、报告、用量不变。归档复验另建干净副本，不信任ZIP中的成功声明。规则hash变化不自动继承旧通过结果，历史accepted不等于当前门禁仍接受。

网页执行生命周期独立保存到data/executions/service.sqlite，原规划JSON保持兼容。编码与预览共享同run活动槽，所有异步结果重新检查当前状态和控制代次；停止请求先显示待确认，未知进程保留私有证据并阻断新活动。旧存档迁移保留待协调历史，不推断外部进程已终止。这是单控制器运行，通用验收计划、已有业务代码的持续变更、多Worker及可靠故障恢复仍在后续里程碑，不能由新增接口推定已完成。

## 独立测试提案定义

在现有四工作区中的“代码与验收”增加默认收起的测试提案入口。仅当前双确认且工程设计有效的运行可显式同意预算后生成；查看、修改与审阅免费，生成默认每个运行最多 3 次，普通计划每次最多 60 秒，至少 16 项需求的计划每次最多 120 秒。尝试、私有回执和接口阶段各自保存。JSON定义编辑及依据保存在标签会话，轮询、切换和刷新不覆盖当前输入；迟到或不同来源的响应不能恢复操作许可。错误使用现有当前视口提示，点击定位才打开对应工作区。

服务独立 SQLite 保存提案、版本及驳回与认可历史。验收规则升级后，原冻结联合定义可按完全相同的检查项续认，取得明确的新批准。续认绑定原停止候选，只提供保留源码修复的授权，历史结论继续保留为原策略证据。提案只绑定当前规格/计划/来源/工程及规则；认可为`definition_only/structural_only`且`executed:false`，不是测试报告。模型不读取候选实现和测试结论，本阶段也不编译或运行提案。原固定图书参考验收仍走原独立门禁，规划/模拟任务状态不因此完成。

需求发布及项目删除先经过规划（含模拟活动）、代码执行和提案的共同检查点；生成或未知停止/回执阻断发布和删除，仍允许保存待应用请求。新来源发布后原定义只读。接口契约见API“独立HTTP测试提案”。原11月14日候选组件的独立检查不代表当前重接线版本已经整体放行，本轮结果见STATUS。

## 同项目需求输入变更

网页在同一项目保存待应用输入，支持正文编辑和MD/TXT/DOCX解析、原因、原文差异及版本历史。保存与应用分开，解析和保存不调用模型。应用同时经过规划和执行的项目检查点；任何运行、预览、未知进程或在途权限操作都阻止发布。新源写入项目JSON并同步当前内存，待应用意图和结果保存在独立SQLite，重启核对发布事实，不能把两种存储称为一个事务。

新源使旧run只读并保留原快照/规格/计划/审批/用量；旧代码检查不计入新源通过，也不能预览或交付。新run基于当前源重新编排，但会从上一输入版本的运行继承已保存问题回答，写入`kind:"inherited"`历史并作为模型输入；重复出现的同一问题直接预填并标为“继承自上一版，可修改”，只要求补充新版新增或变化的信息。新版正文优先，冲突由用户修改预填答案。旧审批、任务和检查不继承；规格与计划均须重新确认。`plan.json`记录`inheritedFrom`。界面按项目保留未保存草稿，轮询不重建编辑控件；发现当前源变化时保留原输入，但要求明确载入当前版本后再保存。观察到外部应用也刷新项目权限，不能继续展示旧审批为当前操作。

当前仅实现需求输入版本与保守影响失效，尚未修改已有业务源码或执行数据库迁移。影响中列出的迁移审查与任务重做是后续工作，不能当作已执行结果。

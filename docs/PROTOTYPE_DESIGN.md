# 当前规划原型实现说明

本文保留当前已实现原型的设计说明。后续协作开发的设计基线见 [当前设计](DESIGN.md)，目标设计不代表下述代码能力已经升级。

本项目面向软件开发需求，将用户文档转换为设计规格、架构建议和可导出的 `task.md`。工作台展示规划阶段的真实执行过程，并在导出前保留人工审阅点。目标软件的编码任务是生成物，不在本原型中自动执行。

2026 年 11 月 14 日新增独立受控编码试验模块，先验证固定纯函数任务的文件修改、代码版本和受限业务检查，尚未连接以下规划工作流。真实模型与可信固定候选分别标注，执行记录不改变规划 Run 的完成含义；接口和限制见 API 的“独立编码试验”。

随后在该独立命令入口接入同候选版本的固定测试服务与Review模型门禁：两个副本分别检查，两方通过且阻塞问题关闭才计为固定任务验收通过。修复后新提交重新检查；测试侧仍为平台固定用例服务，尚不是自主生成用例的测试Agent。浏览器工作流与下述规划Run状态保持原义。

2026年11月14日继续实现workflowVersion=2的网页双确认：spec后awaiting_spec，答复问题并保存修订、确认规格后才生成架构/任务；review后awaiting_review，确认当前计划后导出。旧run沿用原行为。版本修订/驳回/过期确认、快照与历史详见API；下图的两条确认门禁现已生效，文档成功仍不代表软件已编码。

## 端到端流程

```mermaid
flowchart LR
    U[上传或粘贴软件需求] --> P[创建项目并保存需求快照]
    P --> I[读取需求文档]
    I --> S[整理设计规格]
    S --> A[设计项目架构]
    S --> T[拆解开发任务]
    A --> R[检查依赖与需求覆盖]
    T --> R
    R --> H[等待人工审阅]
    H -->|确认并附审阅意见| E[导出 Markdown 与结构化计划]
```

前端从后端读取状态、事件和产物，不自行推测进度。每个阶段成功时才发布相应产物；失败阶段的后继被阻塞，独立分支仍可完成。原始需求和生成物共同保存在对应项目的运行记录中。

## 模块和数据流

前端负责输入、模式选择、运行控制、依赖图、日志和文档预览。HTTP 服务验证输入与状态，再调用编排器或读取已发布产物。规划器只返回结构化数据和文本；执行器不会执行用户文档中的代码。

| 模块 | 职责 | 主要输入输出 |
| --- | --- | --- |
| 文档解析 | 接收 UTF-8 文本或提取 DOCX 正文，限制文件与文本大小。 | 上传内容 → 需求文本 |
| 规划器 | 提取规格、生成开发任务、渲染文档、检查覆盖与依赖。 | 需求文本 → 规格、任务、Markdown |
| 编排器 | 按依赖启动阶段，推进状态，处理审阅、暂停与重试。 | 运行与操作 → 阶段状态、事件、产物 |
| 本地存储 | 保存项目、不可变需求引用和每次运行记录。 | 项目对象 → 原子写入的 JSON |
| 前端工作台 | 展示规划过程和开发计划，提供可执行的用户操作。 | API 状态 → 图、日志、预览和下载 |

每个项目可以多次运行。一个项目同一时刻只允许一个执行中、暂停或等待审阅的运行，避免用户误将多个活动过程混为一份结果。再次运行创建新的 `run_id`；失败重试沿用当前运行并递增对应阶段的 `attempt`。

## 需求规格和来源

需求解析得到标题、摘要、目标、角色、编号需求、约束、全局验收场景、假设、待确认问题和技术边界。每条编号需求包含描述、验收建议、类别和 `sourceQuote`，下游开发任务通过 `requirementIds` 关联需求。

本地规则模式按章节区分上下文与实现范围。项目背景进入目标，角色单独保留，功能与约束形成编号需求；验收场景进入规格和集成验证，待确认事项留作问题。若没有独立功能章节但角色中包含操作，可将这些操作作为功能候选。该模式适合离线演示和快速初稿，仍不能判断所有业务关系：一段话中的多个行为可能需要继续拆分。未给出的选型、工期和负责人保留为待确认项。

模型模式将文档作为数据发送给配置的 Chat Completions 兼容服务。返回规格必须满足结构要求，并且每个原文引用都逐字存在于需求文档中；不满足时，规格阶段失败。模型只协助整理规格，其余步骤沿用同一组确定性生成和校验规则。

## 开发任务与两张依赖图

工作台同时处理两种图，需要分别理解：

- **规划工作流图**表示本工具正在执行的文档处理阶段。节点成功表示相应计算或文档已完成。
- **开发任务图**表示未来目标软件的候选开发计划。节点初始均为待开发，任务包含建议修改位置和验收条件。

本地开发任务模板先创建工程基线和领域契约，再为每条编号需求生成实现或约束任务，最后安排集成验证与交付。模块任务初步共享领域契约依赖；真正的业务先后关系由团队审阅确定。程序检查图中任务编号唯一、依赖目标存在、自环和循环依赖。

审查还检查每条需求是否至少关联一个开发任务、任务是否含验收条件、任务是否引用未知需求。结构通过不能证明设计完全正确，因此审阅门禁保留在导出之前。

## 编排状态和控制

| 阶段状态 | 含义 |
| --- | --- |
| `pending` | 尚未开始；只有全部前置阶段成功才可运行。 |
| `running` | 已被调度，当前尝试正在执行。 |
| `succeeded` | 执行成功且产物已经发布。 |
| `failed` | 当前尝试失败，保留错误与历史记录。 |
| `blocked` | 前置阶段失败，当前阶段无法继续。 |

编排器最多并行启动两个可运行阶段，因此架构与任务拆解可以并行。在本地模式下，默认增加 350 毫秒阶段观察间隔，便于前端展示变化；配置为零时去除该间隔，调度规则保持一致。

运行状态包括执行中、暂停、等待审阅、成功和失败。所有阶段成功后运行成功；没有可执行或执行中阶段且存在失败或阻塞时运行失败。检查阶段成功后，导出阶段保持待执行，运行进入 `awaiting_review`。仅此状态接受人工确认，审阅意见写入交接文档。

暂停属于阶段边界暂停。已启动阶段允许结束，编排器不再启动后继；恢复后重新检查依赖。停止服务或进程中断不等同于暂停：重启时会把执行中和暂停的运行转为中断失败，以便用户明确选择重试；已完成和等待审阅的记录保持可查看。

## 失败和重试

阶段异常会记录任务、尝试次数、时间和原因，并将尚未执行的后继标为阻塞。独立分支继续执行，待运行结束后才允许重试，避免与尚未完成的分支产生状态冲突。

重试选定的失败节点时，编排器保留成功分支和已发布的产物，重新检查后继的所有依赖。还有其他失败前置时，后继仍不能启动。日志和尝试历史累计保存，便于解释“第一次失败、第二次成功”的过程。

演示选项支持指定阶段首次失败，用于复核分支保留与恢复逻辑。该故障会显示在日志中。原始需求无效、模型配置错误等真实问题仍需修正输入或配置，不能承诺点击重试一定成功。

## 可视化交互

界面包含项目导航、模式和运行选择、规划工作流、开发任务、阶段详情、执行事件和产物预览。所有更改经后端校验，连续点击不能重复启动同一有效操作。

工作流节点配合文字和颜色显示状态。任务详情展示需求来源、依赖、修改位置和验收。事件按递增序号排列，前端轮询合并结果；选择节点、文本输入和审阅意见不能因为刷新而丢失。产物可在发布后单独查看与下载，完整 ZIP 包在确认导出成功后开放。

Markdown 内容作为文本安全渲染，需求中的 HTML 不作为页面代码运行。服务端默认只监听回环地址，密钥仅在服务端读取；需求与产物保存在本地，使用模型模式时需求内容会发送给所配置的服务。

## 产物和持久化

| 产物 | 负责阶段 | 作用 |
| --- | --- | --- |
| `spec.md` | 规格 | 保存需求、原文引用与未确定项。 |
| `architecture.md` | 架构 | 提供模块、领域对象和接口边界建议。 |
| `task.md` | 任务 | 提供编号任务、依赖、修改位置和验收条件。 |
| `review.md` | 检查 | 保存结构检查、需求覆盖和人工审阅清单。 |
| `handoff.md` | 导出 | 保存文档清单、审阅意见和后续开发步骤。 |
| `plan.json` | 导出 | 提供机器可读的规格、任务和检查结果。 |

所有运行归属一个项目，保存于 `data/<project-id>.json`，通过临时文件加重命名方式写入。下载包另附 `requirements.md`，保存用于本次规划的需求文本。具体接口见 [API 约定](API.md)。

## 首版验收

1. 导入任意一份示例需求，跑通规格、架构、任务、检查和人工导出，得到真实文档。
2. 改用另一份业务需求，规格与任务内容随输入变化，原文引用可逐项查到。
3. 所有需求都有开发任务映射，任务包含依赖和验收，非法图被拒绝。
4. 注入一次任务拆解失败，架构分支保留；重试成功后进入审阅，已成功阶段不重复运行。
5. 暂停后不启动后继，恢复后继续；重复操作被后端拒绝。
6. 刷新页面或重启服务后可查看历史记录；中断的运行有明确失败状态。
7. DOCX 输入提取正文，非法或超限文件有明确提示。
8. 模拟模型输出覆盖合法响应、错误引用和服务错误，真实模型连通性按使用者配置另行验证。

本地单用户运行、固定规划工作流和确定性的任务模板构成首版范围。未来若要自动执行开发任务，需要另外定义仓库访问、执行器、产物检查与失败恢复协议，不能把规划节点成功直接解释为目标软件已完成。

## 当前独立Web执行范围

浏览器工作台目前仍采用上述规划子流程；独立CLI已具备固定`library-web-v1`的多文件生成、Git候选、SQLite应用受控运行、HTTP/浏览器/模型Review同版本门禁及源码交付。首个真实模型候选已通过完整固定业务检查并完成干净目录启动，事实及失败历史见[VERIFICATION](VERIFICATION.md)。这不是从任意上传需求自动生成复杂项目的通用能力。

生成应用只导出`createApp({databasePath})`及有界请求处理接口；平台固定worker在无网络、源只读的MXC中调用，宿主将随机localhost端口的HTTP转为有界stdio消息。数据库只写当前私有数据目录，验收在独立快照和数据库运行。浏览器会话使用单独Cookie命名空间及来源限制。源码包保护启动外壳在导入可信runtime前检查哈希；不直接在宿主执行生成的应用模块。

已有模型候选可以在不改代码的情况下建立新版本复验记录，完整重跑固定检查和新Review；原提交、报告、用量不变。归档复验另建干净副本，不信任ZIP中的成功声明。网页执行接口、通用验收计划、持续需求变更、多Worker及故障协调仍在后续里程碑，不能由这些CLI组件推定已完成。

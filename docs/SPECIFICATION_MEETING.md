# 多 Agent 规格评审 v0.2

本轮实现依据用户提供的《Taskflow 多 Agent 规格评审方案 v0.2.docx》。首版通过离线角色模型夹具展示完整门禁与交互，不发出真实模型请求，不提供真实业务充分性评审结论。会议通过只允许继续规划，不是代码、测试或软件交付通过。

## 流程

手动规划到达规格确认停点后，点击「启用本版离线评审」。历史运行及未启用的规划沿用原流程；一旦启用，本运行必须完成当前版本会议并联合确认，不能改用普通规格确认绕过。自动交付运行不能启用此离线入口。

| 节点 | 实际执行与门禁 |
| --- | --- |
| 确认需求基线 | 固定原文快照、已确认答复、规格版本及需求覆盖表；检查来源、需求主责、独立审阅和专业覆盖。 |
| 形成专业提案 | 各业务域及交互、数据、权限、接口、可靠性席分别读取同一基线，形成带条款、来源、异常及可观察结果的规则提案。保守保留所有专业维度，不以关键词取消必审席。 |
| 讨论并决策 | 按议题关联各席异议，逐项记录选项和影响。原文或已确认答复明确时引用原句修订；否则复用「查看问题」由用户逐题选择。产生实际新规格后，全席重新检查。 |
| 汇编设计规格 | 保存当前规格、覆盖和决议；主责结构自测通过后，专业席、验收席及独立 Review 检查同一产物哈希。 |
| 确定阶段 Review 要求 | 对架构、任务、验收设计、开发、集成、交付生成输入版本、产物、主责、必审、方法、证据、阻塞条件与依赖；各阶段负责人和独立席审阅。清单是定义，所有规则 `executed:false`。 |
| 提交用户确认 | 校对前五节点产物版本、当前规格及清单；产品、验收和独立席通过后等待用户联合确认，才开始原有架构/任务规划。 |

各节点均保存主责自测、固定产物、独立 Review 和尝试历史。专业提案也保留各席自己的结构自测。缺席、超时、无效结果继续等待，可点击继续；Review 退回须实际修改规格并重新启用评审。旧阻塞携带至新轮次，不能靠改标题或切换场景清除，原席须逐项提交满足复核条件的证据。旧版本或不匹配的返回存入尝试记录，不计入放行。

## 版本和保存

会议绑定项目、规划运行、需求内容版本及代次、规格内容版本、已确认答复版本。所有内容保存在原 ProjectStore JSON，复用项目操作锁、保存失败回滚和权限检查。用户答复和来源裁决都生成新的规格内容版本；用户答复另保存到澄清历史。修改来源或已确认答复使旧评审失效。

联合包哈希绑定当前规格、需求覆盖、各节点产物/自测/Review、议题、裁决、历史阻塞和阶段清单。人工确认绑定该哈希及规格版本。新增 `spec-review-minutes.json`、`stage-review-checklist.json` 产物，随原规划 ZIP 导出；纪要保留所有旧轮次和非阻塞保留意见。

页面每次请求推进一个节点；继续按钮可连续推进至业务裁决、退回、等待或联合确认。关闭页面不会偷偷继续评审，刷新/服务重开后读取最后保存状态，再手动继续。不存在持久后台模型 Worker 或收费请求恢复。

## 离线演示

使用 Node.js 22.21 及以上，在仓库执行：

```powershell
npm run spec-review:demo
$env:DATA_DIR = 'output/specification-meeting-demo-data'
$env:PORT = '4321'
npm start
```

演示生成器只写独立演示目录，不修改用户 `data/`，不启动服务器、不确认规格、不调用模型或编码。重复执行会新增演示项目。手动启动后访问 `http://127.0.0.1:4321`，选中「多 Agent 预约规格评审」：

1. 默认场景启用评审，到「讨论并决策」停下。查看数据、权限两条关联异议，点击「查看问题并裁决」，分别原样填写列出的一个选项并继续。
2. 新规格出现后点击「继续离线评审」。核对新版本、六节点证据、决议及阶段清单，再点「确认规格与阶段清单并继续」。架构/任务随后生成，原有计划确认仍保留。
3. 新建演示项目，启用前选择「自测通过但独立 Review 退回」。裁决并重审后，规格节点自测通过但独立席退回。在规格编辑器首条需求验收添加「失败时保持原记录」，保存，启用新版本评审并继续。未满足原条件的无关修改仍被拦住。
4. 另一新项目选择「旧版本 Review 迟到」。旧结果留在尝试记录，后续节点等待；点击继续才接受本版结果。
5. 任意检查点刷新或关闭重开，状态和历史仍在。离线通过后仍不应出现真实测试通过或源码交付资格。

源规则识别刻意收窄：夹具仅识别预约取消的固定权限/时段规则及 Review 失败条件；不能裁定时交用户，不假装支持任意业务语义。用户裁决首版接受列出的准确选项，范围扩展走已有需求变更。会议协议与覆盖可复用到其他规格，但通用业务提案质量需要真实适配器后另行验证。

## 可替换接口与边界

`createApp` 支持注入 `specificationMeetingExecutor`，提供 `propose({seat,spec,source,confirmedAnswers,binding,signal})` 和 `review({role,nodeId,artifact,selfTest,binding,artifactRevision,scenario,attempt,obligations,signal})`。Review 必须返回同一角色、节点、绑定和产物哈希、布尔结论、证据、带位置/影响/复核条件/阻塞标记的意见；已有阻塞必须逐个返回带证据的 `resolutions`。默认 `OfflineSpecificationRoles` 仅使用本地确定性规则。

单次角色等待默认 3 秒，最多 20 轮、每节点 20 次尝试，节点产物上限 2MB；超时不会把稍后返回的结果算作通过。这不是持久模型请求、预算或取消适配器。未实现真实多模型席位调用、动态席位配置、通用语义审阅、跨运行自动复用结论，也未将阶段定义接成新的编码/测试执行。后续真实接入必须补齐协议、预算、取消/未知用量、来源安全及独立质量验收。

本轮免费回归命令为 `npm run spec-review:test`；实际结果见 [验证记录](VERIFICATION.md) 和 [任务记录](tasks/specification-meeting-v02.md)。

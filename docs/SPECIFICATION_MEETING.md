# 多 Agent 规格评审

需求规格评审以用户提供的《Taskflow 多 Agent 规格评审方案 v0.2》为依据。工作台展示每条需求、各专业席和整份设计规格的评审。会议经人工联合确认后可进入工程规划。软件测试和交付继续使用各自的证据门禁。

## 流程

手动规划到达规格确认停点后，点击项目页「处理规格」或流程图里的「确认规格」，进入「规划与确认」的「多 Agent 规格评审」。有待补充问题时先处理问题。可选「启用本版离线评审」或「启用本版模型评审」。模型入口在规格、工程、验收和 Review 服务配置齐全时显示，点击授权向配置服务发送需求原文和规格材料，服务商可能计费。启用会议后，本运行的放行条件是完成当前版本并联合确认。历史和未启用的运行沿用原流程，自动交付使用独立入口。

| 节点 | 实际执行与门禁 |
| --- | --- |
| 确认需求基线 | 固定原文快照、已确认答复、规格版本及需求覆盖表；检查来源、需求主责、独立审阅和专业覆盖。 |
| 形成专业提案 | 系统从需求条款生成稳定议题编号。业务席和相关专业席先读取相同的议题和来源，分别提交独立提案。全部首轮提案固定后才进入交叉质疑，审阅角色收到同一议题的目标提案和其他席位的观点摘要。质疑回执绑定提案和交叉上下文的版本。 |
| 汇总并分流 | 汇总提案异议和交叉质疑。引用可核对原文的缺项进入规格修订。跨条款冲突保留相关编号和复核条件。涉及未确认业务取舍时开放现有裁决入口。无法安全归类的问题留给主笔核对。有效裁决可推动新版本，未关闭的必审问题继续阻挡规格发布。 |
| 汇编设计规格 | 保存当前规格、需求覆盖、业务决议和已通过的专业提案版本及规则引用。专业席、验收席与独立席检查同一份汇编产物。 |
| 确定阶段 Review 要求 | 逐条需求定义可观察行为、格式、主责自检、独立席及返工条件。架构、任务、验收设计、开发、集成、交付各有输入版本、证据、阻塞条件及依赖。各阶段负责人和独立席审核定义，规则状态为 `executed:false`。 |
| 提交用户确认 | 校对前五节点产物版本、当前规格及清单；产品、验收和独立席通过后等待用户联合确认，才开始原有架构/任务规划。 |

工作台的「议题讨论」按条款展示独立提案和具名质疑。「问题分流」显示原文、影响和复核条件，并可在返工停点跳到对应规格编辑字段。功能 Review 与阶段门禁分别可读，无具体格式时标记待定义。同一版本的继续尝试复用已签收的提案和质疑。修订或裁决换版后启动新轮次，原阻塞携带，由原席逐条复核。旧版或不匹配的返回留在尝试记录。

## 版本和保存

会议绑定项目、规划运行、需求内容版本及代次、规格内容版本、已确认答复版本。所有内容保存在原 ProjectStore JSON，复用项目操作锁、保存失败回滚和权限检查。用户答复和来源裁决都生成新的规格内容版本，用户答复另保存到澄清历史。换版会保留未决阻塞议题和来源，即使新一轮的角色未再次提出该问题。若受影响条款已从规格中移除，需要先核对实际需求范围或恢复条款。修改来源或已确认答复使旧评审失效。

联合包哈希绑定规格、需求覆盖、各节点及专业提案、裁决、历史阻塞、逐条定义和阶段清单。新轮次还绑定议题和分流记录。人工确认绑定该哈希及规格版本。可在规划产物查看 `spec-review-minutes.json`、`stage-review-checklist.json` 和 `reviewed-design-specification.json`，计划确认后随原规划 ZIP 导出。纪要保留各版轮次与保留意见。

页面每个服务器请求推进一个节点。继续按钮顺序推进，遇到业务裁决、退回、等待或联合确认即停。刷新或重开服务后可从最近保存状态手动继续。模型派发前持久保存额度预留。单个运行最多 384 次请求，每轮根据需求数量缩减上限并计入此前轮次用量。单次模型请求约 45 秒超时。若服务中断，未结算预留保守计入额度，远端用量保留未知。角色服务地址与模型需和本运行选用配置一致。

## 离线演示

使用 Node.js 22.21 及以上，在仓库执行：

```powershell
npm run spec-review:demo
$env:DATA_DIR = 'output/specification-meeting-demo-data'
$env:PORT = '4321'
npm start
```

演示生成器只写独立演示目录，不修改用户 `data/`，不启动服务器、不确认规格、不调用模型或编码。重复执行会新增演示项目。手动启动后访问 `http://127.0.0.1:4321`，选中「多 Agent 预约规格评审」：

1. 默认场景启用评审，到「讨论并决策」停下。查看数据、权限两条关联异议，点击「查看问题并裁决」，分别原样填写列出的一个选项并继续。
2. 新规格出现后点击「继续离线评审」。核对新版本、六节点证据、决议及阶段清单，再点「确认规格与阶段清单并继续」。架构/任务随后生成，原有计划确认仍保留。
3. 新建演示项目，启用前选择「自测通过但独立 Review 退回」。裁决并重审后，规格节点自测通过但独立席退回。在规格编辑器首条需求验收添加「失败时保持原记录」，保存，启用新版本评审并继续。未满足原条件的无关修改仍被拦住。
4. 另一新项目选择「旧版本 Review 迟到」。旧结果留在尝试记录，后续节点等待；点击继续才接受本版结果。
5. 任意检查点刷新或关闭重开，状态和历史仍在。离线通过后仍不应出现真实测试通过或源码交付资格。

源规则识别刻意收窄：夹具仅识别预约取消的固定权限/时段规则及 Review 失败条件；不能裁定时交用户，不假装支持任意业务语义。用户裁决首版接受列出的准确选项，范围扩展走已有需求变更。会议协议与覆盖可复用到其他规格，但通用业务提案质量需要真实适配器后另行验证。

## 可替换接口与边界

`createApp` 可注入 `specificationMeetingExecutor`，实现 `propose({seat,spec,source,confirmedAnswers,binding,topics?,signal})` 和 `review({role,nodeId,proposalSeat?,artifact,selfTest,binding,artifactRevision,scenario,attempt,obligations,signal})`。新轮次提案请求的 `topics` 只包含议题和来源。交叉质疑的 `artifact.discussion` 包含同议题其他立场。Review 回执必须匹配角色、节点、提案和产物版本，并包含结论、证据和可复核的意见，既有阻塞通过 `resolutions` 逐个复核。默认 `OfflineSpecificationRoles` 使用确定性夹具。模型模式通过配置的 Chat Completions 服务发起独立无工具调用，由平台绑定席位和版本，并按结构校验输出。

离线单次席位等待默认 3 秒。每运行最多 20 轮、每节点最多 20 次尝试，单份节点产物上限 2MB。当前角色逻辑固定，同一个模型服务可承接多个独立角色。模型适配通过本机模拟 HTTP 服务回归，多模型语义审阅质量及供应商实际计费待实测。后续开发、测试及交付门禁在本工作台展示定义。

免费回归命令为 `npm run spec-review:test`。可查看 [验证记录](VERIFICATION.md) 和 [分层 Review 任务记录](tasks/specification-review-chain.md)。

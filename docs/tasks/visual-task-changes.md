# 任务修改与功能添加的可视化流程

## 目标与基线

基线：`main/f036eff`，开始时工作副本干净。用户希望更方便地修改后续开发任务，并明确选择“填写功能说明，由系统更新需求并重新规划”的新增功能方式。

本轮验收目标：从任务图进入既有任务编辑，选择前置任务和关联需求、预览改动并保存新计划；从任务图填写新增功能，预览需求追加内容、保存待应用请求，在安全检查点应用新版需求，再由用户显式启动重新规划。每个成功状态均来自已确认的后端结果，旧版本和审批规则保留。

## 修改边界与交互

- 根 Agent：`public/app.js`、`public/planning-review.js`、`public/styles.css`、集成浏览器测试和文档。
- 功能添加 Agent：`public/source-changes.js`及其单元/浏览器回归。
- 任务分析 Agent：`public/task-plan-view.js`和纯函数回归。
- 后端版本绑定 Agent：`lib/orchestrator.mjs`及独立创建运行回归。
- 不新增付费自动调用，不修改用户数据，不扩展真实编码范围和存储格式；创建运行接口兼容增加可选的预期需求双版本，防止多窗口晚到请求启动未核对的需求版本。

沿用当前蓝白工作台：正文与背景采用现有字体和配色（白色`#ffffff`、浅蓝`#f7f9ff`、正文`#344c6d`、操作蓝`#315deb`、确认绿`#16846a`），用任务节点、依赖选择、改动前后对照和顺序步骤表达信息。窄屏改为单列，键盘焦点与草稿在刷新/轮询中保留，不用装饰性动画。

任务图的“修改此任务”定位到对应编辑区。计划内的依赖和来源用带标题的选项选择，展示未保存的具体改动及可能需要一起核对的下游任务；依赖校验仅用于及时反馈，后端仍为最终判据。已确认导出的计划和历史运行保持只读，后续业务修改通过需求新版本重新规划。

新增功能采用名称、描述、验收条件表单，将预览内容追加到现有需求草稿，保留用户已有修改。保存请求不应用版本，应用版本不自动调用模型；重新规划仍需用户明确操作，并沿用现有预算提示与双确认。

## 验证计划

运行语法检查、任务差异/依赖及需求草稿回归、实际Edge桌面与390px操作，核对编辑定位、保存与版本变化、重复追加防护、输入与焦点保留、异常提示、历史只读和控制台。完成集成后再运行必要的相关回归；不以模拟模型测试宣称真实新增业务已实现。

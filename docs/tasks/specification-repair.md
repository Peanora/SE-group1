# 规格失败定位与补充修改

## 目标

修正“整理设计规格”在需求不清晰或模型条目无法追溯时只显示通用失败、用户不知道问题在哪也无法修改的问题。要求：

- 失败节点显示具体问题类型、可定位的需求序号/标题（若模型返回了该位置）、剩余调用次数和下一步。
- 对可修正的规格失败提供固定字段的补充编辑区，至少覆盖目标、使用者、首版范围、不包含项、验收标准和依据说明。
- 补充信息可先免费保存；只有用户显式选择“保存并重新整理”才新增一次冻结预算内的模型请求。
- 原始需求快照不变；补充内容作为新的需求来源进入规格问答历史，重新生成的规格仍需人工确认。
- 非用户信息问题（模型超时、网络、凭据、保存失败等）不能伪装成“需求没写清楚”。

## 基准与范围

基准为 `5aaae2e`（main，工作副本干净）。改动范围：规格解析错误分类、失败DTO、新增运行action、网页失败面板、回归与接口/原型文档。未改固定参考代码执行、模拟编排、SQLite执行生命周期或用户 `data/`。

## 实现

- `lib/specification-failure.mjs`：新增固定reason/label/message、可选需求位置、可公开的控制器校验说明，以及按失败类型选择的补充字段。模型原始响应、私有路径和异常正文不进入DTO。
- `lib/planner.mjs`：将空需求、需求过多、条目缺字段、缺验收、引用不匹配、缺标题/摘要、缺技术边界等分别归类，并携带需求序号/标题。引用片段仍不公开，保留原有隐私断言。
- `lib/planning-review.mjs`：模型响应已保存但后置规格校验失败时标记为规格校验失败，不再误记为`stale_revision`。
- `lib/orchestrator.mjs`：
  - `describeRun`派生`specificationFailure.supplement`（fields/saved/canRetry/note）。
  - 新增`supplement_spec`：`retry:false`只保存`specificationRepair`草稿；`retry:true`校验预算后把补充写入`clarificationHistory`（`kind:"spec_repair"`），重置规格及下游阶段并重新调度。
  - 直接重试失败规格时，若存在同需求版本的补充草稿，先提交草稿，避免用户保存的内容被忽略。
  - 所有路径再次核对项目/运行/来源版本，预算耗尽、未知字段、超长、其他活动运行均拒绝。
- `public/spec-repair.js` + `index.html` + `app.js` + `styles.css`：失败节点下方显示诊断和字段表单；支持免费保存、预算内重新整理、跳转到原始需求修改入口；桌面和390px均可操作，刷新后从服务器草稿恢复。
- `public/planning-review.js`：历史记录显示“补充规格信息”操作。

## 限制

- 仍未实现从失败私有响应中直接编辑或删除模型条目；用户通过补充来源或修改原始需求修正，再消耗预算重试。
- 补充字段的问题文本是平台固定模板，不保证模型下一轮一定采纳；模型输出仍需人工确认。
- 未验证真实付费模型的语义质量；本轮所有模型响应为模拟响应。未读取或改写用户现有失败运行，仅离线只读核对真实失败回执可派生“第20条需求”诊断。
- 原文快照仍按运行冻结；大范围修改应使用现有“修改当前项目需求”流程并重新编排。

## 后续

在本地工作台用现有失败项目核对诊断与补充表单，由用户自行决定是否消耗剩余1次调用；如模型仍不采纳补充，可改用原始需求修改生成新运行。真实模型质量验证另行授权，不自动调用。

# 需求变更后继承已确认回答

## 问题

用户修改/增加需求并“再次编排”时，新运行从空规格开始，模型会把上一版已经明确过的问题再次提出，用户需要重复回答；旧运行只读虽保证历史，但增量体验差。

## 实现

- `Orchestrator.inheritedClarifications`：仅当项目有多代输入时工作。默认选择上一输入版本中带已回答问题或`clarificationHistory`的最近运行；也接受显式`inheritFromRunId`，但必须属于本项目且绑定上一输入版本。
- 收集上一运行`specQuestions`答复和`clarificationHistory`答复，按问题文本去重，写入新运行`clarificationHistory`的`kind:"inherited"`轮次；附带`inheritedFrom`元数据。回答参与模型输入、引用白名单和规格来源，但不继承旧审批、任务、计划、检查或执行许可。
- 若新规格重复同一问题文本，`prepareSpec`预填继承答案并标记`inherited`，同步`spec.clarifications`并重算`specRevision`；用户可直接核对或修改，无需重填。不同措辞的问题仍作为新问题。
- 继承内容超过100000字符时从最旧轮次开始收缩，保留能适配的最新回答；没有可继承回答时不创建空历史。
- `plan.json`写入`inheritedFrom`；`spec.md`对继承回答标注`[继承上一版]`；页面提示继承数量和新版正文优先，问题标签显示“继承自上一版，可修改”。
- 旧`sourceSuperseded`运行仍只读；新规格/计划仍需两次人工确认。需求变更的保守影响分析不变，不声称旧代码或旧验收可复用。

## 验证

- `npm run check`：117脚本语法通过。
- `npm test`：707项，677通过、30跳过、0失败、0取消，114,761.8115ms。30项跳过为未启用真实MXC/显式真实Edge的既有集成项。
- 新增回归：
  - 需求输入应用后创建新运行，继承上一版2条回答，`inheritedFrom.answerCount=2`、历史为`kind:"inherited"`、审批为空、快照为新正文。
  - 新版规格重复旧问题时预填继承答案、标记`inherited`，`spec.clarifications`同步且`specRevision`与规格内容一致。
  - 既有澄清、回复、输入变更、导出、工程自动修正和可复现验收回归全部通过。
- 未调用真实付费模型；未修改用户现有运行数据。

## 限制

- 只按问题文本精确匹配预填；模型换一种问法仍会作为新问题出现，用户需补充。
- 继承的是用户旧答案，不是旧规格/代码；新版正文与旧答案冲突时以正文为准，需用户修改。
- 旧审批、任务、检查、执行和交付许可均不继承，仍需完整重新规划和确认。
- 仅复用同一项目上一输入版本的运行；跨版本链通过新运行自身携带的继承历史继续。

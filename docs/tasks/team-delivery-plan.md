# Taskflow 六人开发分工

本轮围绕从确认需求到交付可运行 Web 项目的主流程。五位组员分别实现一个可用功能，在自己的分支完成自测。组长负责定范围、合并分支和整体验收。团队统一从包含首页流程图的 `2b22924` 开始。

| 大方向 | 人员 | 本轮交付 |
| --- | --- | --- |
| 代码开发与执行 | 组员 2、组员 3 | 识别编码输出截断，修复长流程运行误停 |
| 代码审查 | 组员 4 | 把同一代码版本的 Review 结论和阻塞项做成可读页面 |
| 独立测试与软件交付 | 组员 5、组员 6 | 增加联合验收清单预览，完善源码包复验诊断 |
| 集成与验收 | 组长 | 统一共享契约和分支，实跑完整流程 |

## 一 代码开发与执行

这个方向有两条链路。组员 2 负责模型返回建议到生成 Git 候选，组员 3 负责在受控环境运行候选。工单试跑曾发生模型输出被截断，采购长流程曾因正常响应占用日志额度而中断。 [阶段记录](../STATUS.md) · [采购诊断](../VERIFICATION.md#2026-11-19-采购留出与运行器响应预算诊断)

### 组员 2 实现编码输出截断诊断

- 在编码模型适配器为 `finish_reason=length` 返回明确的错误类型，保留原始回执和用量归属。
- 在执行记录和首页失败提示中显示「编码输出被截断」，给出缩小任务可写范围后再试的操作说明。完整响应中的格式错误仍走已有的有界格式修正。
- 自测使用两种本地模拟回包。完整有效回包能生成 Git 候选。截断回包有可读诊断，部分文件写入数、发出的 Review 请求数及自动重试次数均为零。
- 主要文件为 `lib/project-code-model.mjs`、`lib/planned-web-executor.mjs`、`lib/planned-failure-help.mjs`。复用编码模型和候选修复测试。

### 组员 3 修复长流程运行误停

- 从已有采购诊断提取最小复现，在运行器中分别计算 HTTP 响应协议数据和应用日志的累计额度。
- 两类额度分别遵守上限，超限后记录具体来源，并验证子进程已停止。新运行规则的接线和历史交付兼容由组长统一核对。
- 自测连续完成 12 次约 24 KB 的合法响应，然后分别验证日志和响应协议超限都会停止。保留实际检查项和通过条件。
- 主要文件为 `lib/web-runtime.mjs`，复用 `tests/web-runtime.test.mjs` 和已有的采购输出预算诊断。

## 二 代码审查

平台的 Review 根据已确认规格审查固定候选代码，报告规则遗漏、权限问题和潜在回归。现有执行顺序是自检后并行运行 HTTP 与浏览器检查，两者通过后再对同一 Git 提交发起 Review。有效的未关闭阻塞会拦住交付。 [审查契约](../API.md#原生review-v2及失败反馈i13完整testi14接线定向复验)

### 组员 4 实现可读的 Review 问题面板

- 在「代码与验收」的 Review 区展示当前候选提交、审查状态、有效问题的位置和证据。每条问题使用后端已有的文件、行号、说明和状态。
- 把未关闭阻塞放在最上面，其余意见按已有级别和状态展示。给尚未审查、审查失败、已审查且零阻塞各自明确的显示。
- 自测用两条不同候选记录切换，一个有阻塞，一个已完成且零阻塞。核对问题和提交对应，阻塞记录的交付入口依旧不可用，历史意见可回看。
- 主要文件为 `public/planned-execution.js` 和 `tests/planned-execution-panel.test.mjs`。读取现有结果字段，沿用后端审查与发布门禁。

## 三 独立测试与软件交付

组员 5 负责编码前如何核对要测的功能，组员 6 负责拿到源码包后如何复验。两项都可以先用固定清单和现有交付包开发。

### 组员 5 实现联合验收清单预览

- 在「验收准备」为选中的清单增加只读预览，展示 HTTP 检查的请求和断言，以及浏览器检查的操作、目标和预期结果。有需求编号时显示对应编号。
- 切换清单时更新预览，保留已有 JSON 编辑和版本确认入口。载入清单只展示待执行的检查；软件是否通过取自实际验收记录。
- 自测用一份联合清单和一份历史 HTTP 清单。切换后步骤与当前选择相符，缺少浏览器检查时有说明，浏览预览期间审批和模型请求均为零。
- 主要文件为 `public/verification-plans.js` 和 `tests/verification-plans-panel.test.mjs`。

### 组员 6 实现源码包复验诊断

- 改进 `planned:verify` 的结果提示，首轮区分文件找不到、包损坏或规则不兼容、缺少运行环境三类。使用安全的错误分类，复用现有报告和退出码。
- 成功时列出 HTTP、浏览器检查数量及报告位置。复验结论继续对应包内可运行检查，历史 Review 资格沿用平台原有记录。
- 自测准备一个缺失路径、一个损坏包和一个有效包。核对各自结果与退出码，确认有效包仍可运行原有检查。
- 主要文件为 `scripts/verify-planned-delivery.mjs`，可复用 `tests/planned-archive.test.mjs` 的归档夹具。

## 四 组长的集成与验收

1. **开工前**确认共享基线、演示样例和字段接口。各人提交一份实现、正常及异常场景的自测结果，以及最短复现步骤。日常自测使用模拟模型和临时数据。
2. **合并时**由组长统一修改共享路由和接口契约。先合编码诊断与运行器，再接 Review 和清单预览，最后用旧包和新包验证复验命令。核对规则升级后每份历史交付的版本归属。
3. **最终验收**用值班留言板同类小项目，在一个集成提交上从首页确认计划和清单，执行真实受控编码、独立 HTTP 与双视口 Edge 检查及同版本 Review，再预览、下载和复验源码包。另用采购预算复现核对长流程。组长记录实际提交、测试结果及尚未通过的事项。 [现有交付样例](../VERIFICATION.md#2026-11-19-登录清单自动接续与真实留言板交付)
